Configuring the Edge Component means three things, whichever provider you are on:

1. Add the workflow that runs on Issue and Issue comment events.
2. Store the provider's ingestion secret so the workflow can send it as `X-JIFFY-TOKEN`.
3. Point the workflow at your Gateway's endpoint URL for that provider.

Nothing else needs to be configured. The Edge Component holds no other state.

## The two settings every provider needs

| Setting | What it is | Where it comes from |
|---|---|---|
| Ingestion secret | The shared secret sent in the `X-JIFFY-TOKEN` header | Generated for you in the Gateway's `.env` as `GITHUB_INGEST_TOKEN`, `GITLAB_INGEST_TOKEN`, or `GITEA_INGEST_TOKEN` |
| Gateway endpoint URL | The full address of the ingestion route for this provider | Your Gateway's public base URL, plus the provider's ingestion path |

The endpoint URL is your Gateway base URL followed by the route for the provider the workflow runs on:

| Provider | Endpoint |
|---|---|
| GitHub | `https://gateway.example.com/api/github/ingestion` |
| GitLab | `https://gateway.example.com/api/gitlab/ingestion` |
| Gitea | `https://gateway.example.com/api/gitea/ingestion` |

<Callout type="warn">
Store the ingestion secret as a repository or project secret — never inline it in the workflow file, and never paste it into an Issue or a Pull Request description. Anyone holding it can submit tasks to your Gateway through that provider's route.
</Callout>

## GitHub Action

<Steps>
<Step>
### Store the secret

In the repository, go to **Settings → Secrets and variables → Actions** and add:

- `JIFFY_INGEST_TOKEN` — the value of `GITHUB_INGEST_TOKEN` from your Gateway's `.env`
- `JIFFY_GATEWAY_URL` — your Gateway endpoint, for example `https://gateway.example.com/api/github/ingestion`

The Gateway endpoint is not sensitive, so it can be stored as a variable rather than a secret if you prefer.
</Step>

<Step>
### Add the workflow

Create the workflow file in the repository so it runs on Issue and Issue comment events:

```yaml title=".github/workflows/jiffy.yml"
name: Jiffy Edge Component

on:
  issues:
    types: [opened, edited]
  issue_comment:
    types: [created, edited]

jobs:
  forward:
    runs-on: ubuntu-latest
    steps:
      - name: Detect mention and forward the Issue thread
        env:
          JIFFY_INGEST_TOKEN: ${{ secrets.JIFFY_INGEST_TOKEN }}
          JIFFY_GATEWAY_URL: ${{ vars.JIFFY_GATEWAY_URL }}
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: |
          # Exit early unless the event body contains a valid @jiffy mention,
          # then collect the full Issue thread and POST it to the Gateway with:
          #   X-JIFFY-TOKEN: $JIFFY_INGEST_TOKEN
```

The `GITHUB_TOKEN` above is only used to read the Issue thread from within the workflow run. It is not the token that later pushes a branch or opens a Pull Request — that one is configured on the Gateway side.
</Step>
</Steps>

## GitLab pipeline job

<Steps>
<Step>
### Store the secret

In the project, go to **Settings → CI/CD → Variables** and add:

- `JIFFY_INGEST_TOKEN` — the value of `GITLAB_INGEST_TOKEN` from your Gateway's `.env`. Mark it **Masked** and **Protected**.
- `JIFFY_GATEWAY_URL` — for example `https://gateway.example.com/api/gitlab/ingestion`
</Step>

<Step>
### Add the pipeline job

GitLab does not start a pipeline on Issue activity on its own, so the job is triggered by a project webhook configured for **Comments** and **Issues** events, which fires a pipeline trigger:

```yaml title=".gitlab-ci.yml"
jiffy-edge:
  stage: .pre
  rules:
    - if: $CI_PIPELINE_SOURCE == "trigger"
  script:
    # Exit early unless the event body contains a valid @jiffy mention,
    # then collect the full Issue thread and POST it to $JIFFY_GATEWAY_URL with:
    #   X-JIFFY-TOKEN: $JIFFY_INGEST_TOKEN
```

<Callout type="info">
Set the webhook to deliver both Issue events and comment events. A mention that arrives in a follow-up comment is the most common way a task is started, and it is missed entirely if only Issue events are delivered.
</Callout>
</Step>
</Steps>

## Gitea Action

<Steps>
<Step>
### Store the secret

In the repository, go to **Settings → Actions → Secrets** and add:

- `JIFFY_INGEST_TOKEN` — the value of `GITEA_INGEST_TOKEN` from your Gateway's `.env`
- `JIFFY_GATEWAY_URL` — for example `https://gateway.example.com/api/gitea/ingestion`

Make sure Actions are enabled for the repository and that a runner is registered and online — a Gitea repository with Actions disabled silently never runs the workflow.
</Step>

<Step>
### Add the workflow

Gitea Actions use the same workflow syntax as GitHub Actions:

```yaml title=".gitea/workflows/jiffy.yml"
name: Jiffy Edge Component

on:
  issues:
    types: [opened, edited]
  issue_comment:
    types: [created, edited]

jobs:

    steps:

        env:
          JIFFY_INGEST_TOKEN: ${{ secrets.JIFFY_INGEST_TOKEN }}
          JIFFY_GATEWAY_URL: ${{ secrets.JIFFY_GATEWAY_URL }}
        run: |
          # Exit early unless the event body contains a valid @jiffy mention,
          # then collect the full Issue thread and POST it to the Gateway with:
          #   X-JIFFY-TOKEN: $JIFFY_INGEST_TOKEN
```
</Step>
</Steps>

## Rotating an ingestion secret

Because each provider's secret is independent, rotating one never affects the others:

1. Generate a new value and set it on the Gateway for that provider only.
2. Update `JIFFY_INGEST_TOKEN` in every repository whose Edge Component uses that provider.
3. Restart the Gateway so it picks up the new value.

Until step 2 is complete on a given repository, that repository's Edge Component receives an authentication failure from the Gateway — see [Troubleshooting](/docs/submodules/edge-component/introduction/troubleshooting).
