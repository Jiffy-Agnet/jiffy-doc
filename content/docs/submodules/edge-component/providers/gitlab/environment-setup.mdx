Everything the Edge Component needs on GitLab is stored in the project, under **Settings → CI/CD → Variables**, plus the pipeline trigger token that lets the webhook start the pipeline in the first place.

## What to configure

| Name | Where | Value | Flags |
|---|---|---|---|
| `JIFFY_INGEST_TOKEN` | Settings → CI/CD → Variables | The value of `GITLAB_INGEST_TOKEN` from your Gateway's `.env` file | Masked |
| `JIFFY_GATEWAY_URL` | Settings → CI/CD → Variables | Your Gateway base address plus `/api/gitlab/ingestion` | None |
| Pipeline trigger token | Settings → CI/CD → Pipeline trigger tokens | Generated by GitLab | Shown once only |

## The X-JIFFY-TOKEN value

`JIFFY_INGEST_TOKEN` is the secret the job sends in the `X-JIFFY-TOKEN` header. The Gateway validates it against the secret configured for the GitLab ingestion route.

Three properties matter:

- **It is generated for you.** The Gateway's `install.sh` writes `GITLAB_INGEST_TOKEN` into `.env` on first run. You do not invent this value.
- **It is per-provider.** The GitLab secret is valid on `/api/gitlab/ingestion` only. It is never shared with the GitHub or Gitea routes, so a leaked GitLab secret cannot be used to submit tasks through another provider.
- **It is not your GitLab token.** It authenticates the Edge Component to your Gateway. It grants no access to GitLab at all.

<Callout type="warn">
Anyone holding this value can submit tasks to your Gateway through the GitLab route. Never inline it in `.gitlab-ci.yml`, never print it in a job log, and never paste it into an Issue or a Merge Request description.
</Callout>

## Masked and Protected

GitLab's two variable flags cause more setup failures than anything else on this provider, because one of them silently removes the variable rather than reporting an error.

| Flag | Effect | Recommendation |
|---|---|---|
| **Masked** | GitLab replaces the value with `[masked]` wherever it appears in job output | Enable it. It only affects logging, never the value the job receives |
| **Protected** | The variable is exposed **only** to pipelines running on protected branches or tags | Enable it only if the Edge Component pipeline actually runs on a protected branch |

If **Protected** is enabled and the pipeline runs on an unprotected branch, the variable is simply not present. The job receives an empty value, sends an empty `X-JIFFY-TOKEN` header, and the Gateway responds with an authentication failure. Nothing in GitLab's interface flags this as a misconfiguration.

<Callout type="warn">
Masking has a value-format requirement — GitLab refuses to mask a value containing certain characters or shorter than its minimum length. If the Masked checkbox will not stay enabled, regenerate the ingestion secret rather than saving it unmasked.
</Callout>

## The Gateway endpoint address

`JIFFY_GATEWAY_URL` is the full address of the GitLab ingestion route:

```text
https://gateway.example.com/api/gitlab/ingestion
```

Check three things:

| Requirement | Why |
|---|---|
| Uses `https` | The ingestion secret travels in a request header and must not cross the network unencrypted |
| Ends in `/api/gitlab/ingestion` | Posting to another provider's path causes the Gateway to validate against that provider's secret, which fails |
| Reachable from the runner | The request is made by the runner, not by GitLab itself. A self-managed runner inside your network can reach a private Gateway; a shared runner on GitLab.com cannot |

## The pipeline trigger token

This token is unique to GitLab. It does not authenticate anything to the Gateway — it authorizes the project webhook to start a pipeline.

- It is created under **Settings → CI/CD → Pipeline trigger tokens** and displayed only once.
- It is embedded in the webhook address, so it is exposed if webhook encryption verification is disabled. Leave verification enabled.
- Revoking it stops all Issue-triggered pipelines for the project immediately, which makes it a clean way to disable Jiffy on a project without removing any configuration.

## What is not configured here

The git provider token — the one that pushes the branch and opens the Merge Request — is **not** stored in the project. It lives on the Gateway, because the push happens later, from inside the sandbox, long after the job has ended.

| Credential | Stored on | Used by |
|---|---|---|
| `JIFFY_INGEST_TOKEN` | GitLab, in the project | The Edge Component |
| Pipeline trigger token | GitLab, in the project | The project webhook |
| Git provider token | The Gateway | The Agent, inside the sandbox |
| `OPENROUTER_API_KEY` | The Gateway | The Agent's model backend |

See the Ecosystem [Prerequisites](/docs/ecosystem/installation/prerequisites) page for the scopes the git provider token needs.

## Rotating the ingestion secret

Because each provider's secret is independent, rotating the GitLab one never affects GitHub or Gitea:

1. Set a new value for `GITLAB_INGEST_TOKEN` on the Gateway and restart it.
2. Update `JIFFY_INGEST_TOKEN` in **every** project whose Edge Component targets GitLab.
3. Trigger a test mention on one project to confirm the new value is accepted.

Between steps 1 and 2, a project still holding the old value receives an authentication failure from the Gateway. Rotate during a quiet period if you have many projects connected.

## Verifying the configuration

Open an Issue and post a note mentioning `@jiffy`, then confirm all four:

- The webhook's **Recent events** view shows a delivery with a successful response.
- A pipeline with source `trigger` appears under **Build → Pipelines**, running the `jiffy-edge` job.
- The Gateway logs a request on `/api/gitlab/ingestion` and queues a task.
- The completion report is posted back as a note on the Issue.

If the job runs but the Gateway rejected the request, the status code identifies the cause — see [Troubleshooting](/docs/submodules/edge-component/introduction/troubleshooting).
