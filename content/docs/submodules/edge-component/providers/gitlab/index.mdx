GitLab is a git provider available both as a hosted service and as software you run yourself. Alongside repository hosting it provides an Issue tracker and a built-in pipeline system, configured through a `.gitlab-ci.yml` file at the root of the project. Jiffy uses the Issue tracker to receive a request and a pipeline job to run the Edge Component.

GitLab calls a repository a **project**, and calls a proposal to merge a branch a **Merge Request** rather than a Pull Request. Both terms appear in GitLab's own interface; elsewhere in these documents the general term Pull Request is used.

## What GitLab provides to Jiffy

| Capability | What Jiffy uses it for |
|---|---|
| Issue tracker | Where a person mentions `@jiffy` to request work, and where the completion report is posted |
| Pipelines | The runtime that executes the Edge Component job |
| Project webhooks | The bridge that turns Issue activity into a pipeline run |
| Continuous integration variables | Storage for the ingestion secret and the Gateway endpoint address |
| Merge Requests | Where the Agent delivers its finished work for review |

## How a GitLab task flows

```
  Issue or comment      ┌──────────────┐        ┌──────────────────┐         ┌───────────────┐
  mentioning @jiffy ──▶ │   Project    │ ─────▶ │  Pipeline job    │ ──────▶ │    Gateway    │
  on your project       │   webhook    │ starts │  runs the Edge   │  POST   │ authenticates │
                        │  (Issues +   │  the   │  Component       │ /api/   │  and queues   │
                        │  Comments)   │pipeline└──────────────────┘ gitlab/ └───────────────┘
                        └──────────────┘                             ingestion
```

## The one structural difference from the other providers

This is the important thing to understand before setting GitLab up, and the reason its configuration has an extra step.

**GitLab pipelines do not start on Issue activity.** Pipelines are designed around code events — pushes, tags, merge requests — and there is no pipeline trigger for "an Issue comment was posted." GitHub Actions and Gitea Actions both support Issue events natively; GitLab does not.

The bridge is a **project webhook**. GitLab delivers Issue and comment events to a webhook, and that webhook starts the pipeline containing the Edge Component job. The extra piece is one webhook and one pipeline trigger token — everything after that is identical to the other providers.

## The destination route

The Edge Component running on GitLab posts to the Gateway's GitLab ingestion route, and only that route:

| Method | Path |
|---|---|
| `POST` | `/api/gitlab/ingestion` |

The request carries the GitLab ingestion secret in the `X-JIFFY-TOKEN` header. That secret is valid on this route alone — it cannot be used against the GitHub or Gitea ingestion routes, and those secrets cannot be used here.

## Three tokens, three purposes

GitLab involves one more credential than the other providers, because of the webhook bridge. Keeping them apart avoids the most common setup mistakes:

| Credential | Used by | Purpose |
|---|---|---|
| Ingestion secret | The Edge Component | Authenticates the job to your Gateway in the `X-JIFFY-TOKEN` header |
| Pipeline trigger token | The project webhook | Lets the webhook start the pipeline that contains the Edge Component job |
| Git provider token | The Agent, inside the sandbox | Pushes the branch and opens the Merge Request on GitLab |

The first two are stored on GitLab, in the project. The third is configured on the Gateway.

<Callout type="warn">
Do not use the automatically provided `CI_JOB_TOKEN` as the git provider token. It is scoped to a single job and expires when that job ends, while the Agent pushes and opens its Merge Request asynchronously, well after that.
</Callout>
