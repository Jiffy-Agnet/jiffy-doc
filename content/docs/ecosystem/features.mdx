## Multi-provider support

Jiffy treats GitHub, GitLab, and Gitea as first-class, interchangeable entry points. Each provider gets its own Edge Component and its own ingestion endpoint and shared secret on the Gateway, but all three feed the same task pipeline — there's no "primary" provider with the others bolted on afterward.

- **GitHub** — a GitHub Action triggers on new Issues and Issue comments.
- **GitLab** — a small webhook relay triggers on Issue and comment events (GitLab CI has no native mention-triggered job for this).
- **Gitea** — a Gitea Action, written in plain `bash` + `curl`/`jq` since Gitea Actions doesn't support GitHub's JS-based actions.

## Isolated sandbox execution

Every task runs in its own ephemeral container — a preconfigured image with the language toolchains and provider command-line tools the agent might need. The container works against an isolated copy of the repository, and is torn down once the task finishes.

The Gateway's worker never touches the host's container runtime directly. A proxy layer sits in between and exposes only the specific operations the worker needs — so a misbehaving or compromised task can't reach anything else on the host.

## Concurrent task execution

Jiffy doesn't process tasks one at a time. The Gateway places incoming tasks on a queue and dispatches them across a pool of workers, so multiple `@jiffy` mentions — even across different repositories or different providers — can be running in their own sandbox at the same time. A long-running task on one repository doesn't block a quick one queued right after it.

Each concurrent task gets its own ephemeral container and its own copy of the target repository, so tasks never share sandbox state, even when two tasks touch the same codebase at once. How many workers run concurrently is a configuration setting rather than a fixed limit, so a team can scale it up for a busier Issue tracker or keep it minimal for lighter workloads.

## Model-agnostic coding agent

The coding agent that runs inside the sandbox isn't wired to one specific AI provider or model. Which large language model powers it is a configuration choice, set once rather than hardcoded into the pipeline.

- Teams can point Jiffy at whichever model fits their needs — a hosted API, a self-hosted model, or a mix across different environments.
- Upgrading to a newer or stronger model, or moving off a provider entirely, doesn't require any change to the Edge Component, the Gateway, or how Pull Requests get created and reported.
- Model choice can vary by environment — for example, a faster and cheaper model for routine tasks and a stronger one reserved for harder ones, if a team chooses to set it up that way.

## Automated PR delivery

The agent doesn't just write code — it finishes the job. It commits its changes, pushes a new branch (auto-named from the task if you didn't specify one, e.g. `Jiffy/add-rate-limiting`), and opens a Pull Request. A summary of what was done, with a link to the PR, is posted back as a comment on the originating Issue, so the whole task lifecycle is visible in one thread.

## Thin-Gateway design

The Gateway's job is deliberately narrow: authenticate a request, queue it, run it in a sandbox, and report back. All provider-specific logic — detecting a mention, assembling the Issue thread, formatting the callback — lives in the Edge Component, not the Gateway. That keeps the Gateway simple to run and reason about, and keeps provider quirks from leaking into the core pipeline.

<Callout type="info">
This split is what makes multi-provider support possible without multiplying the Gateway's complexity — adding a provider means writing an Edge Component against the existing ingestion contract, not extending the Gateway itself.
</Callout>

## Extensible to future channels

Because the Gateway only cares about receiving a well-formed, pre-filtered task payload, the entry point doesn't have to be a git provider's Issue tracker. The same ingestion contract can be satisfied by a chat app integration (e.g. a Telegram or Slack bot) or a direct API call — channels currently on the roadmap — without changing anything downstream of the Gateway.
