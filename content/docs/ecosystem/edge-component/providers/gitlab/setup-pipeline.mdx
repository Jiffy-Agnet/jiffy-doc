This page walks through configuring the GitLab pipeline job that runs the Edge Component. GitLab needs one more step than the other providers — a project webhook that turns Issue activity into a pipeline run — so work through the steps in order.

## Before you start

You need the value of `GITLAB_INGEST_TOKEN` from your Gateway's `.env` file, your Gateway's public base address, and the Maintainer role on the project (webhooks and trigger tokens both require it). If you have not installed the Gateway yet, start with the Ecosystem [Installation](/docs/ecosystem/installation/quickstart) page.

<Steps>
<Step>
### Store the ingestion secret

In the project, go to **Settings → CI/CD → Variables** and select **Add variable**.

- **Key** — `JIFFY_INGEST_TOKEN`
- **Value** — the value of `GITLAB_INGEST_TOKEN` from your Gateway's `.env` file
- **Type** — Variable
- **Flags** — enable **Masked** so the value is hidden in job logs, and enable **Protected** only if the pipeline runs on protected branches

Add the Gateway address the same way, without the masking flags, since it is not sensitive:

- **Key** — `JIFFY_GATEWAY_URL`
- **Value** — your Gateway base address followed by the GitLab ingestion path, for example `https://gateway.example.com/api/gitlab/ingestion`

<Callout type="warn">
If **Protected** is enabled on `JIFFY_INGEST_TOKEN` but the pipeline runs on an unprotected branch, the variable is simply absent at run time — the job receives an empty value and the Gateway rejects the request. When in doubt, leave Protected disabled and keep Masked enabled.
</Callout>

</Step>

<Step>
### Create a pipeline trigger token

The webhook needs permission to start a pipeline. Go to **Settings → CI/CD → Pipeline trigger tokens** and add a new token, describing it as something like `jiffy-edge-component`.

GitLab shows the token value once. Copy it now — you need it in the next step, and it cannot be retrieved afterward.

<Callout type="info">
📷 Screenshot placeholder — insert a screenshot here showing: the Settings → CI/CD → Pipeline trigger tokens section with a newly created token described as jiffy-edge-component.
</Callout>
</Step>

<Step>
### Add the project webhook

This is the bridge that makes Issue activity start a pipeline. Go to **Settings → Webhooks** and add a webhook pointing at the project's pipeline trigger address, using the token from the previous step.

Under **Trigger**, enable both:

- **Issues events** — a new Issue is opened or its description is changed
- **Comments** — a note is added to an Issue

Both are required. Enabling only Issues events misses every mention posted as a follow-up comment, which is how most tasks are actually requested.

<Callout type="warn">
Leave **Enable SSL verification** on. The webhook carries the trigger token, and disabling verification exposes it.
</Callout>

<Callout type="info">
📷 Screenshot placeholder — insert a screenshot here showing: the webhook edit form with the Issues events and Comments trigger checkboxes selected and SSL verification enabled.
</Callout>
</Step>

<Step>
### Add the pipeline job

Add the Edge Component job to `.gitlab-ci.yml` at the root of the project:

```yaml title=".gitlab-ci.yml"
jiffy-edge:
  stage: .pre
  rules:
    - if: $CI_PIPELINE_SOURCE == "trigger"
  script:
    # 1. Exit immediately unless the event body contains a valid @jiffy mention.
    # 2. Collect the full Issue thread: the original description plus every comment.
    # 3. POST that thread to $JIFFY_GATEWAY_URL with the header:
    #      X-JIFFY-TOKEN: $JIFFY_INGEST_TOKEN
```

The `rules` block is what keeps this job out of your normal pipelines. `$CI_PIPELINE_SOURCE == "trigger"` restricts it to pipelines started by the webhook, so an ordinary push never runs the Edge Component.

</Step>

<Step>
### Confirm a runner is available

A GitLab job only runs if a runner can pick it up. On GitLab.com, shared runners are available by default. On a self-managed instance, confirm under **Settings → CI/CD → Runners** that at least one runner is online and, if it uses tags, that the job's tags match.

A job that no runner accepts sits pending indefinitely and never reports an error.

<Callout type="info">
📷 Screenshot placeholder — insert a screenshot here showing: the Settings → CI/CD → Runners section with at least one runner shown as online and available to the project.
</Callout>
</Step>

<Step>
### Verify the request reaches the Gateway

Open a test Issue and post a comment mentioning `@jiffy`. Then check each stage of the chain in turn:

- **The webhook** — under **Settings → Webhooks**, the **Recent events** view shows the delivery and the response GitLab received.
- **The pipeline** — under **Build → Pipelines**, a new pipeline with source `trigger` should appear, containing the `jiffy-edge` job.
- **The Gateway** — the logs should show a request on `/api/gitlab/ingestion` and a task queued for that Issue.

Checking in this order isolates the failure immediately: no webhook delivery means the trigger configuration is wrong; a delivery but no pipeline means the trigger token or the address is wrong; a pipeline but no Gateway request means the mention was not detected or the variables are missing.

</Step>
</Steps>

## Where the request is sent

| Property | Value |
|---|---|
| Method | `POST` |
| Path | `/api/gitlab/ingestion` |
| Full address | `$JIFFY_GATEWAY_URL`, for example `https://gateway.example.com/api/gitlab/ingestion` |
| Authentication header | `X-JIFFY-TOKEN: <the GitLab ingestion secret>` |
| Body | The full Issue thread — the original description plus every comment |

If the job runs but the Gateway rejects the request, see [Troubleshooting](/docs/submodules/edge-component/introduction/troubleshooting) for what each status code means. Continue to [Environment Setup](/docs/submodules/edge-component/providers/gitlab/environment-setup) for the complete list of variables and their flags.
