An Issue is how work is requested from Jiffy on GitLab. There is no separate queue, dashboard, or command interface — the Issue thread is both the request and the record.

## How GitLab tracks Issues

Every GitLab project has a built-in Issue tracker. An Issue has a title, a **description**, and an ordered list of **notes** — GitLab's word for comments. That structure is what Jiffy consumes: the thread is the task specification.

| Part of the Issue | How Jiffy uses it |
|---|---|
| Title | Context for the task, and the basis of the automatically derived branch name |
| Description | The original request, read as part of the requirements |
| Notes (comments) | Later clarifications, corrections, and the mention itself |
| Thread order | Preserved, so the Agent can tell an earlier rejected approach from the current one |

## Registering a task

<Steps>
<Step>
### Open an Issue, or use an existing one

Describe what you want done in ordinary language. Both paths work equally well:

- **A new Issue** — write the request in the description and mention `@jiffy` there.
- **An existing Issue** — add a note mentioning `@jiffy`, once the thread already contains enough context.

The second form is the common one. A discussion happens, the requirement settles, and someone then hands it to Jiffy.
</Step>

<Step>
### Mention Jiffy

Write `@jiffy` followed by the instruction, for example:

```text
@jiffy add a health-check endpoint that returns the service version
```

The mention can appear anywhere in the description or note — beginning, middle, or end.
</Step>

<Step>
### The webhook starts the pipeline

GitLab delivers the Issue or comment event to the project webhook, which starts a pipeline containing the `jiffy-edge` job. This is the step that has no equivalent on the other providers, and it is where a GitLab-specific failure usually shows up first.
</Step>

<Step>
### The Edge Component evaluates the event

The job's first action is to check for a valid mention. If none is present it exits immediately, no request is made, and the Gateway never learns the event happened.

Note the consequence of the webhook bridge: on GitLab a pipeline runs for **every** Issue and comment event, including those with no mention at all. Most of those pipelines do nothing but exit. That is expected, and it is why the job is scoped to trigger pipelines only.

<Callout type="info">
📷 Screenshot placeholder — insert a screenshot here showing: an Issue note containing an @jiffy instruction, with the resulting triggered pipeline visible in the project's pipeline list.
</Callout>
</Step>

<Step>
### The full thread is collected and forwarded

Once the mention is confirmed, the Edge Component collects the **entire** thread — the original description plus every note, in order — not just the note that carried the mention. That complete thread is posted to `/api/gitlab/ingestion`.
</Step>

<Step>
### The report comes back to the same thread

When the task finishes, the completion report is posted as a note on the same Issue, with a link to the Merge Request. The thread that started the task is also where the result lands.

</Step>

## How the mention is validated

Mention matching is exact and deliberately narrow. A mention is treated as a task request only when all of the following hold:

| Condition | Detail |
|---|---|
| The text matches the configured mention | Matching is exact. A different spelling or a different name does not match |
| It appears in an Issue description or a note | Other event types, such as a label change or an assignment, carry no new text to match against |
| It is not inside a fenced code block | Text in a code block is documentation or an example, never an instruction |
| It is not inside a quoted reply | Quoting an earlier message that mentioned Jiffy does not re-trigger the task |

The last two rules exist so that writing about Jiffy in an Issue does not accidentally start a task. Discussing the mention in a code block is safe.

<Callout type="warn">
GitLab's own autocomplete may offer a real GitLab user or group whose name resembles the configured mention. Selecting it inserts a reference to that account rather than plain text, which changes what is written in the description. Type the mention out rather than accepting an autocomplete suggestion.
</Callout>

<Callout type="info">
GitLab also treats Merge Request discussions as notes. The Edge Component acts on Issue threads only — a mention posted on a Merge Request does not start a task.
</Callout>

## One task per Issue at a time

The Gateway holds a lock for each Issue with a task in flight. A second mention on the same Issue while the first task is still running is acknowledged with `202 Accepted` and `{"status": "already_queued"}`, and no second task is created.

This is what prevents one Issue from producing two sandboxes, two branches, and two competing Merge Requests. Once the first task finishes, mentioning Jiffy again on the same Issue starts a new task normally.

If a mention produced no reaction at all, check the webhook's **Recent events** view first — on GitLab, a missing webhook delivery is the most common cause. See [Troubleshooting](/docs/submodules/edge-component/introduction/troubleshooting) for the rest.
