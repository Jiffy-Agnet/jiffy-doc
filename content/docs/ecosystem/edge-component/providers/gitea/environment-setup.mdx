Gitea configuration has two layers, and this is what distinguishes it from the other providers: the repository holds the secrets, but the instance itself has to be prepared first. A perfectly configured repository does nothing on an instance where Actions is disabled or no runner is registered.

## What to configure

| Name | Where | Value | Sensitive |
|---|---|---|---|
| `JIFFY_INGEST_TOKEN` | Settings → Actions → Secrets | The value of `GITEA_INGEST_TOKEN` from your Gateway's `.env` file | Yes |
| `JIFFY_GATEWAY_URL` | Settings → Actions → Variables, or Secrets | Your Gateway address plus `/api/gitea/ingestion` | No |

Whether **Variables** is available depends on your Gitea version. If it is present, put the Gateway address there — it is not sensitive and staying readable makes it easier to verify. If it is not, storing both as secrets works and changes nothing functionally.

## Instance-level requirements

Confirm all three before troubleshooting anything in the repository:

| Requirement | Where | Symptom if missing |
|---|---|---|
| Actions enabled on the instance | `app.ini`, `[actions] ENABLED = true` | No workflow in any repository ever runs, with no error shown |
| At least one act runner registered and online | Site Administration → Actions → Runners | Runs are created but stay pending indefinitely |
| Actions unit enabled on the repository | Settings → Repository | No run is created at all for that repository |

All three fail quietly. None of them produces a message in the Issue thread, which is why they are worth checking first rather than last.

## The X-JIFFY-TOKEN value

`JIFFY_INGEST_TOKEN` is the secret the workflow sends in the `X-JIFFY-TOKEN` header. The Gateway validates it against the secret configured for the Gitea ingestion route.

Three properties matter:

- **It is generated for you.** The Gateway's `install.sh` writes `GITEA_INGEST_TOKEN` into `.env` on first run. You do not invent this value.
- **It is per-provider.** The Gitea secret is valid on `/api/gitea/ingestion` only. It is never shared with the GitHub or GitLab routes, so a leaked Gitea secret cannot be used to submit tasks through another provider.
- **It is not your Gitea token.** It authenticates the Edge Component to your Gateway. It grants no access to Gitea at all.

<Callout type="warn">
Anyone holding this value can submit tasks to your Gateway through the Gitea route. Never inline it in the workflow file, never print it in a workflow log, and never paste it into an Issue or a Pull Request description.
</Callout>

## The Gateway endpoint address

`JIFFY_GATEWAY_URL` is the full address of the Gitea ingestion route. On a self-hosted setup this is frequently an internal address:

```text
https://gateway.internal.example.com/api/gitea/ingestion
```

Check three things:

| Requirement | Why |
|---|---|
| Uses encrypted transport | The ingestion secret travels in a request header. A private network is not by itself a reason to send it unencrypted |
| Ends in `/api/gitea/ingestion` | Posting to another provider's path causes the Gateway to validate against that provider's secret, which fails |
| Resolves **from the runner** | The runner makes the request, not Gitea. An address that works from your own machine may not resolve on the runner host |

The last point is the one that catches people out. If the runner runs in a container, `localhost` refers to that container, not to the host — use the host's address on the shared network, or the service name if the Gateway and the runner share a container network.

## What is not configured here

The git provider token — the one that pushes the branch and opens the Pull Request — is **not** stored in the repository. It lives on the Gateway, because the push happens later, from inside the sandbox, long after the workflow run has ended.

| Credential | Stored on | Used by |
|---|---|---|
| `JIFFY_INGEST_TOKEN` | Gitea, in the repository | The Edge Component |
| Git provider token | The Gateway | The Agent, inside the sandbox |
| `OPENROUTER_API_KEY` | The Gateway | The Agent's model backend |

The git provider token is a Gitea access token with the `repo` and `issue` scopes. See the Ecosystem [Prerequisites](/docs/ecosystem/installation/prerequisites) page for the full list.

## Rotating the ingestion secret

Because each provider's secret is independent, rotating the Gitea one never affects GitHub or GitLab:

1. Set a new value for `GITEA_INGEST_TOKEN` on the Gateway and restart it.
2. Update `JIFFY_INGEST_TOKEN` in **every** repository whose Edge Component targets Gitea.
3. Trigger a test mention on one repository to confirm the new value is accepted.

Between steps 1 and 2, a repository still holding the old value receives an authentication failure from the Gateway. Rotate during a quiet period if you have many repositories connected.

## Verifying the configuration

Open an Issue and post a comment mentioning `@jiffy`, then confirm all three:

- The workflow run appears under the repository's **Actions** tab and finishes successfully rather than staying pending.
- The Gateway logs a request on `/api/gitea/ingestion` and queues a task.
- The completion report is posted back as a comment on the Issue.

A run that stays pending is a runner problem, not a configuration problem. A run that fails at the forwarding step with an authentication failure means the secret or the address is wrong — see [Troubleshooting](/docs/submodules/edge-component/introduction/troubleshooting).
