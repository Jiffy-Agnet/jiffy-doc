This page walks through creating the Gitea Action that runs the Edge Component. Gitea needs the runtime prepared before anything else — Actions enabled and a runner registered — so work through the steps in order.

## Before you start

You need the value of `GITEA_INGEST_TOKEN` from your Gateway's `.env` file, your Gateway's address as reachable from the runner, and administrative access to the Gitea instance for the first step. If you have not installed the Gateway yet, start with the Ecosystem [Installation](/docs/ecosystem/installation/quickstart) page.

<Steps>
<Step>
### Enable Actions on the instance

Gitea Actions is disabled by default on many instances. In the instance configuration file, `app.ini`, confirm:

```ini title="app.ini"
[actions]
ENABLED = true
```

Restart Gitea after changing this. Without it, no workflow in any repository runs, and no error is reported anywhere in the web interface.

<Callout type="info">
📷 Screenshot placeholder — insert a screenshot here showing: the Site Administration area confirming that Actions is enabled on the instance.
</Callout>
</Step>

<Step>
### Register an act runner

Gitea provides no hosted runners, so you supply the machine that executes workflows. Install the act runner, then register it against your instance with a registration token obtained from **Site Administration → Actions → Runners**, or from the repository's own runner settings for a repository-scoped runner.

Once registered, the runner appears in that list with a status of idle or online. A runner shown as offline accepts nothing.

<Callout type="warn">
The runner is what makes the request to the Gateway, not Gitea itself. Whatever address you configure in the next steps must resolve and be reachable from the machine where the runner is installed.
</Callout>

<Callout type="info">
📷 Screenshot placeholder — insert a screenshot here showing: the Runners administration page with a registered act runner listed as idle, including its labels.
</Callout>
</Step>

<Step>
### Enable Actions on the repository

In the repository, go to **Settings → Repository** and enable the **Actions** unit. This is a per-repository switch, separate from the instance-level setting, and both must be on.

<Callout type="info">
📷 Screenshot placeholder — insert a screenshot here showing: the repository's Settings page with the Actions unit checkbox enabled.
</Callout>
</Step>

<Step>
### Store the ingestion secret

In the repository, go to **Settings → Actions → Secrets** and add:

- **Name** — `JIFFY_INGEST_TOKEN`, with the value of `GITEA_INGEST_TOKEN` from your Gateway's `.env` file
- **Name** — `JIFFY_GATEWAY_URL`, with your Gateway address followed by the Gitea ingestion path, for example `https://gateway.internal.example.com/api/gitea/ingestion`

Gitea's variables support varies by version. If the release you run offers **Settings → Actions → Variables**, store `JIFFY_GATEWAY_URL` there instead, since the address is not sensitive. Otherwise storing both as secrets works.

<Callout type="warn">
Paste the secret value directly rather than retyping it, and make sure no trailing newline or space is included. A value with trailing whitespace is a different string, and the Gateway rejects it with an authentication failure.
</Callout>

<Callout type="info">
📷 Screenshot placeholder — insert a screenshot here showing: the repository's Settings → Actions → Secrets page with JIFFY_INGEST_TOKEN and JIFFY_GATEWAY_URL both listed.
</Callout>
</Step>

<Step>
### Add the workflow file

Create the workflow at `.gitea/workflows/jiffy.yml`. The syntax matches GitHub Actions:

```yaml title=".gitea/workflows/jiffy.yml"
name: Jiffy Edge Component

on:
  issues:
    types: [opened, edited]
  issue_comment:
    types: [created, edited]

jobs:
  forward:
    runs-on: ubuntu-latest
    steps:
      - name: Detect mention and forward the Issue thread
        env:
          JIFFY_INGEST_TOKEN: ${{ secrets.JIFFY_INGEST_TOKEN }}
          JIFFY_GATEWAY_URL: ${{ secrets.JIFFY_GATEWAY_URL }}
        run: |
          # 1. Exit immediately unless the event body contains a valid @jiffy mention.
          # 2. Collect the full Issue thread: the original body plus every comment.
          # 3. POST that thread to $JIFFY_GATEWAY_URL with the header:
          #      X-JIFFY-TOKEN: $JIFFY_INGEST_TOKEN
```

The value of `runs-on` must match a label your registered runner actually advertises. If the runner was registered with different labels, use one of those instead — a job whose label matches no runner sits pending forever.

<Step>
### Understand the trigger events

Two separate events are declared, and both are required:

| Event | Fires when | Why it matters |
|---|---|---|
| `issues` — `opened` | A new Issue is created | Catches a mention written in the original Issue body |
| `issues` — `edited` | An existing Issue body is changed | Catches a mention added to the body afterward |
| `issue_comment` — `created` | A comment is added to an Issue | The most common way a task is started |
| `issue_comment` — `edited` | An existing comment is changed | Catches a mention added to a comment afterward |

Omitting `issue_comment` is the single most common cause of a mention that never triggers anything. Most tasks are requested in a follow-up comment, not in the original Issue body.

<Callout type="info">
📷 Screenshot placeholder — insert a screenshot here showing: the repository's Actions tab with a workflow run listed and its triggering event visible in the run summary.
</Callout>
</Step>

<Step>
### Commit the workflow to the default branch

Like GitHub, Gitea runs Issue-triggered workflows from the repository's **default branch** only. A workflow that exists just on a feature branch never fires.

Commit `.gitea/workflows/jiffy.yml` to your default branch, either directly or by merging a Pull Request that adds it.

<Callout type="info">
📷 Screenshot placeholder — insert a screenshot here showing: the repository's Actions tab listing "Jiffy Edge Component" as an available workflow after the file has been merged to the default branch.
</Callout>
</Step>

<Step>
### Verify the request reaches the Gateway

Open a test Issue and post a comment mentioning `@jiffy`. Then check both ends:

- **On Gitea** — the repository's **Actions** tab should show a new "Jiffy Edge Component" run for the `issue_comment` event, finishing successfully.
- **On the Gateway** — the logs should show a request on `/api/gitea/ingestion` and a task queued for that Issue.

If the run appears but stays pending, the problem is the runner — either none is online, or none advertises the label named in `runs-on`.

</Step>
</Steps>

## Where the request is sent

| Property | Value |
|---|---|
| Method | `POST` |
| Path | `/api/gitea/ingestion` |
| Full address | `$JIFFY_GATEWAY_URL`, for example `https://gateway.internal.example.com/api/gitea/ingestion` |
| Authentication header | `X-JIFFY-TOKEN: <the Gitea ingestion secret>` |
| Body | The full Issue thread — the original body plus every comment |

If the workflow runs but the Gateway rejects the request, see [Troubleshooting](/docs/submodules/edge-component/introduction/troubleshooting) for what each status code means. Continue to [Environment Setup](/docs/submodules/edge-component/providers/gitea/environment-setup) for the complete list of secrets and instance requirements.
