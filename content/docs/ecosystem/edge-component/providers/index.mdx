Every provider needs the same three things configured — something that runs on Issue and comment events, an ingestion secret sent as `X-JIFFY-TOKEN`, and your Gateway's endpoint address for that provider. What differs is how the automation gets triggered in the first place:

| Provider | How it's triggered | Extra piece needed |
|---|---|---|
| GitHub | GitHub Actions supports Issue and comment events natively | None |
| GitLab | Pipelines don't start on Issue activity, so a small webhook relay you host yourself bridges the gap | The relay itself |
| Gitea | Gitea Actions supports Issue and comment events natively | None |

## GitHub

### Overview

GitHub Actions runs the Edge Component directly — no relay or bridge needed. A workflow file in the repository triggers on new Issues and Issue comments, checks for `@jiffy`, and forwards the thread straight to the Gateway.

```
  Issue or comment      ┌──────────────────────┐                     ┌───────────────────┐
  mentioning @jiffy ──▶ │    GitHub Actions    │ ──────────────────▶ │      Gateway      │
  on your repository    │  runs the workflow   │  POST               │  authenticates    │
                        │                      │  /api/github/       │  and queues       │
                        └──────────────────────┘  ingestion          └───────────────────┘
```

The two credentials involved are easy to mix up: the **ingestion secret** authenticates the workflow to the Gateway, while the **git provider token** (a separate, longer-lived PAT) is what the Agent later uses inside the sandbox to push a branch and open the Pull Request. Never use the workflow's default `GITHUB_TOKEN` for that second purpose — it expires before the Agent gets to it, since the push happens asynchronously after the workflow run ends.

### Setting up the Action

<Steps>
<Step>
### Add the repository secrets and variables

Under **Settings → Secrets and variables → Actions**:

| Name | Kind | Value |
|---|---|---|
| `JIFFY_GATEWAY_URL` | Secret | Your Gateway's base URL, e.g. `https://jiffy.example.com` |
| `JIFFY_GITHUB_INGEST_TOKEN` | Secret | The value of `GITHUB_INGEST_TOKEN` from the Gateway's `.env` |
| `JIFFY_REPO_PAT` | Secret | A fine-grained PAT with Contents (Read/Write) and Pull requests (Read/Write) on this repo |
| `JIFFY_BOT_LOGIN` | Variable | The bot account's GitHub login, used to tell agent replies apart from human ones |
| `JIFFY_USER_WHITELIST` | Variable (optional) | Comma-separated GitHub usernames allowed to trigger Jiffy |
</Step>

<Step>
### Add the workflow

Create `.github/workflows/jiffy.yml`:

```yaml title=".github/workflows/jiffy.yml"
name: Jiffy Dispatch

permissions:
  contents: write
  pull-requests: write
  issues: write

on:
  issues:
    types: [opened]
  issue_comment:
    types: [created]

jobs:
  dispatch:
    runs-on: ubuntu-latest
    if: |
      (github.event_name == 'issues' && contains(github.event.issue.body, '@jiffy')) ||
      (github.event_name == 'issue_comment' && contains(github.event.comment.body, '@jiffy'))
    steps:
      - name: Collect thread and dispatch to Jiffy Gateway
        uses: actions/github-script@v9
        env:
          JIFFY_URL: ${{ secrets.JIFFY_GATEWAY_URL }}
          JIFFY_INGEST_TOKEN: ${{ secrets.JIFFY_GITHUB_INGEST_TOKEN }}
          JIFFY_BOT_LOGIN: ${{ vars.JIFFY_BOT_LOGIN }}
          JIFFY_USER_WHITELIST: ${{ vars.JIFFY_USER_WHITELIST }}
          REPO_TOKEN: ${{ secrets.JIFFY_REPO_PAT }}
        with:
          script: |
            const issueNumber = context.payload.issue.number;
            const whitelist = (process.env.JIFFY_USER_WHITELIST || '')
              .split(/[\s,]+/).map(s => s.trim().toLowerCase()).filter(Boolean);
            if (!whitelist.includes(String(context.actor).toLowerCase())) {
              console.log('Not in user_whitelist — skipping.');
              return;
            }

            const issue = await github.rest.issues.get({ ...context.repo, issue_number: issueNumber });
            const comments = await github.paginate(github.rest.issues.listComments, { ...context.repo, issue_number: issueNumber });
            const botLogin = process.env.JIFFY_BOT_LOGIN || '';

            const turns = [
              { role: 'user', author: issue.data.user.login, body: issue.data.body || '', created_at: issue.data.created_at },
              ...comments.map(c => ({
                role: c.user.login === botLogin ? 'agent' : 'user',
                author: c.user.login, body: c.body || '', created_at: c.created_at,
              })),
            ];

            const repoToken = process.env.REPO_TOKEN;
            const payload = {
              repo: { url: `https://github.com/${context.repo.owner}/${context.repo.repo}.git`, token: repoToken, username: context.actor },
              issue: { turns, external_issue_id: String(issueNumber) },
              callback: {
                url: `https://api.github.com/repos/${context.repo.owner}/${context.repo.repo}/issues/${issueNumber}/comments`,
                secret: repoToken,
              },
            };

            const response = await fetch(`${process.env.JIFFY_URL}/api/github/ingestion`, {
              method: 'POST',
              headers: { 'Content-Type': 'application/json', 'X-JIFFY-TOKEN': process.env.JIFFY_INGEST_TOKEN },
              body: JSON.stringify(payload),
            });
            if (response.status >= 400) {
              core.setFailed(`Jiffy ingestion failed: ${response.status} ${await response.text()}`);
            }
```

`issue_comment` matters as much as `issues` — most tasks are requested in a follow-up comment, not in the original Issue body. Omitting it is the most common reason a mention never triggers anything.

<Callout type="warn">
If `JIFFY_USER_WHITELIST` is unset or empty, the workflow posts a one-time comment on the Issue explaining that Jiffy is disabled on the repo and how to enable it, and does not forward anything to the Gateway.
</Callout>
</Step>

<Step>
### Commit it to the default branch

GitHub only runs Issue-triggered workflows from the repository's default branch — one that only exists on a feature branch never fires, no matter how many Issues get opened.
</Step>
</Steps>

### Environment variables

| Variable | Stored on | Sensitive |
|---|---|---|
| `JIFFY_GATEWAY_URL` | Repository (variable) | No |
| `JIFFY_GITHUB_INGEST_TOKEN` | Repository (secret) | Yes |
| `JIFFY_REPO_PAT` | Repository (secret) | Yes |
| `JIFFY_BOT_LOGIN` | Repository (variable) | No |
| `JIFFY_USER_WHITELIST` | Repository (variable, optional) | No |

The ingestion secret is per-provider and generated for you — it's the `GITHUB_INGEST_TOKEN` the Gateway's installer wrote into `.env`, never something you invent. It's only ever valid on `/api/github/ingestion`.

### Example: an Issue from mention to PR

1. Someone opens an Issue, or comments on an existing one, with `@jiffy add a health-check endpoint that returns the service version`.
2. The workflow fires on the `issue_comment` event, confirms the mentioning user is in `JIFFY_USER_WHITELIST`, and collects the full thread — the Issue body plus every comment, in order, not just the one with the mention.
3. It posts that thread to `/api/github/ingestion` with `X-JIFFY-TOKEN` set to `JIFFY_GITHUB_INGEST_TOKEN`. The Gateway queues a task.
4. If you comment `@jiffy` again on the same Issue while that task is still running, the Gateway responds `202 Accepted` with `{"status": "already_queued"}` — expected, not an error.
5. Once the Agent finishes, it pushes a branch and opens a Pull Request, and the Gateway posts a summary with a link to that PR back as a comment on the same Issue.

## GitLab

### Overview

This is the one provider where GitHub Actions/Gitea Actions' native mention-triggered job has no equivalent — **GitLab pipelines don't start on Issue activity at all**. The bridge is a small, stateless webhook relay you host yourself: GitLab delivers Issue and comment webhooks to it, and the relay does the mention check, thread collection, and forwarding in a single step.

```
GitLab webhook (Issues + Comments) ──▶ Relay ──▶ Gateway /api/gitlab/ingestion
```

There's no `.gitlab-ci.yml` job and no Pipeline Trigger Token involved — the relay talks to the Gateway directly over HTTP. It has no database and no queue, so it can run anywhere with network access to both GitLab and the Gateway: a small VM, a container, or a serverless function, ideally placed near your GitLab instance.

<Callout type="warn">
Because the relay owns the entire GitLab-side flow, if it's down every `@jiffy` mention on that project is silently ignored. Monitor its health.
</Callout>

### Setting up the relay

<Steps>
<Step>
### Add the project webhook

Under **Settings → Webhooks**, point a new webhook at your relay's endpoint (e.g. `https://relay.example.com/webhook`), set its Secret Token, and enable **Issues events** and **Comments**. Leave SSL verification on.
</Step>

<Step>
### Run the relay

The relay verifies the `X-Gitlab-Token` header, checks the issue or comment body for `@jiffy`, fetches the full thread via the GitLab API, and POSTs it to the Gateway:

```python title="relay.py (excerpt)"
def do_POST(self):
    token = self.headers.get("X-Gitlab-Token", "")
    if token != GITLAB_WEBHOOK_SECRET:
        self.send_error(401, "Invalid webhook token")
        return

    data = json.loads(self.rfile.read(int(self.headers.get("Content-Length", 0))))
    # ... determine issue_iid and the mentioning text, skip if no "@jiffy" ...

    # Fetch the issue + all notes via the GitLab API, join into one thread
    payload = {
        "repo": {"url": repo_url, "token": GITLAB_API_TOKEN, "username": author_login},
        "issue": {"text": full_thread_text, "external_issue_id": str(issue_iid)},
        "callback": {"url": callback_url, "secret": GITLAB_API_TOKEN},
    }
    requests.post(f"{JIFFY_GATEWAY_URL}/api/gitlab/ingestion", json=payload,
                  headers={"X-JIFFY-TOKEN": JIFFY_INGEST_TOKEN})
```

A complete, ready-to-run version of this script (standard library plus `requests`, no other dependencies) is in the Gateway repository's [`docs/jiffy-gitlab-setup.md`](https://github.com/Jiffy-Agnet/gateway/blob/master/docs/jiffy-gitlab-setup.md) — copy it directly and run it behind a process supervisor (systemd, supervisord, or a container with a restart policy).
</Step>

<Step>
### Verify each stage in order

Open a test Issue, comment `@jiffy`, then check three places in sequence — it isolates the failure immediately:

- **The webhook** — Settings → Webhooks → Recent events shows the delivery and the response your relay sent.
- **The relay's own logs** — did it detect the mention and attempt the request?
- **The Gateway** — a request on `/api/gitlab/ingestion` and a queued task.
</Step>
</Steps>

### Environment variables

These are set on the relay process itself, not as GitLab CI/CD variables — there's no pipeline involved:

| Variable | Description |
|---|---|
| `GITLAB_WEBHOOK_SECRET` | Compared against the incoming `X-Gitlab-Token` header |
| `GITLAB_API_TOKEN` | GitLab PAT/project token with `read_api` + `write_repository`; also used as the callback secret and as the git provider token for pushing/opening the MR |
| `CI_API_V4_URL` | e.g. `https://gitlab.com/api/v4`, or your self-managed instance's API URL |
| `JIFFY_GATEWAY_URL` | Base URL of your Gateway |
| `JIFFY_INGEST_TOKEN` | Must match `GITLAB_INGEST_TOKEN` on the Gateway |

Keep all three credentials — the webhook secret, the API token, and the ingestion token — separate. They're never meant to be reused for each other, and rotating one doesn't affect the others.

### Example: an Issue from mention to PR

1. Someone opens an Issue, or comments on an existing one, with `@jiffy add a health-check endpoint that returns the service version`.
2. GitLab delivers an Issue or Note webhook to your relay. The relay checks `X-Gitlab-Token`, then checks the body for `@jiffy`.
3. If found, it fetches the issue description and every note via the GitLab API, joins them into one thread, and posts it to `/api/gitlab/ingestion` with `X-JIFFY-TOKEN` set to `JIFFY_INGEST_TOKEN`.
4. The Gateway queues a task. A duplicate delivery for the same Issue gets `202 Accepted` with `{"status": "already_queued"}`.
5. Once finished, the Agent pushes a branch and opens a Merge Request. The Gateway POSTs the summary to the GitLab Issue Notes API — the same thread where the task started.

## Gitea

### Overview

Gitea Actions supports Issue and comment events natively, the same as GitHub — no relay needed. The one real difference is that Gitea Actions doesn't support GitHub's JavaScript-based `actions/*` steps (`actions/github-script` and friends don't run on a Gitea runner), so the workflow is written in plain `bash` + `curl` against the Gitea REST API instead.

```
  Issue or comment      ┌──────────────────────┐                     ┌───────────────────┐
  mentioning @jiffy ──▶ │    Gitea Actions     │ ──────────────────▶ │      Gateway      │
  on your repository    │  runs the workflow   │  POST               │  authenticates    │
                        │  (bash + curl)       │  /api/gitea/        │  and queues       │
                        └──────────────────────┘  ingestion          └───────────────────┘
```

### Setting up the Action

<Steps>
<Step>
### Add the repository secrets

Under **Settings → Actions → Secrets**:

| Name | Value |
|---|---|
| `GITEA_ACCESS_TOKEN` | A Gitea token with `repo` + `issue` scope and a long expiry (1 year, or none) |
| `JIFFY_GITEA_INGEST_TOKEN` | Must match `GITEA_INGEST_TOKEN` on the Gateway |
| `JIFFY_GATEWAY_URL` | Base URL of your Gateway |
</Step>

<Step>
### Add the workflow

Create `.gitea/workflows/jiffy.yml` — note the `.gitea/` path, not `.github/`:

```yaml title=".gitea/workflows/jiffy.yml"
name: Jiffy Dispatch

on:
  issues:
    types: [opened]
  issue_comment:
    types: [created]

jobs:
  dispatch:
    runs-on: ubuntu-latest
    if: |
      (github.event_name == 'issues' && contains(github.event.issue.body, '@jiffy')) ||
      (github.event_name == 'issue_comment' && contains(github.event.comment.body, '@jiffy'))
    steps:
      - name: Collect thread and dispatch to Jiffy Gateway
        env:
          GITEA_TOKEN: ${{ secrets.GITEA_ACCESS_TOKEN }}
          JIFFY_URL: ${{ secrets.JIFFY_GATEWAY_URL }}
          JIFFY_INGEST_TOKEN: ${{ secrets.JIFFY_GITEA_INGEST_TOKEN }}
          GITEA_HOST: ${{ github.server_url }}
          OWNER: ${{ github.repository_owner }}
          REPO: ${{ github.event.repository.name }}
          ISSUE_NUMBER: ${{ github.event.issue.number }}
        run: |
          set -e
          ISSUE_JSON=$(curl -s -H "Authorization: token $GITEA_TOKEN" \
            "${GITEA_HOST}/api/v1/repos/${OWNER}/${REPO}/issues/${ISSUE_NUMBER}")
          COMMENTS_JSON=$(curl -s -H "Authorization: token $GITEA_TOKEN" \
            "${GITEA_HOST}/api/v1/repos/${OWNER}/${REPO}/issues/${ISSUE_NUMBER}/comments")
          # Join issue body + all comment bodies with jq, build the payload,
          # then POST it to $JIFFY_URL/api/gitea/ingestion with header
          # X-JIFFY-TOKEN: $JIFFY_INGEST_TOKEN
```

Two Gitea-specific things worth knowing: `github.server_url` resolves to your Gitea instance's own URL (a compatibility feature, not a bug), and every secret needs to go through `env:` rather than being interpolated directly into a `run:` shell string — Gitea masks `env:`-sourced secrets in logs, but raw `${{ }}` interpolation into a shell command can still leak a value via error output.

A complete working version of this workflow (issue and comment fetch, thread assembly with `jq`, and dispatch) is in the Gateway repository's [`docs/gitea_setup.md`](https://github.com/Jiffy-Agnet/gateway/blob/master/docs/gitea_setup.md) — copy it directly into `.gitea/workflows/jiffy.yml`.
</Step>
</Steps>

### Environment variables

| Variable | Stored on | Sensitive |
|---|---|---|
| `GITEA_ACCESS_TOKEN` | Repository secret | Yes |
| `JIFFY_GITEA_INGEST_TOKEN` | Repository secret | Yes |
| `JIFFY_GATEWAY_URL` | Repository secret | No, but stored as a secret here since Gitea Actions has no separate variables tab in older versions |

`GITEA_ACCESS_TOKEN` does double duty: it reads the Issue thread through the Gitea API, and it's the same token the Agent later uses to push the branch and open the Pull Request — which is exactly why it needs a long expiry rather than a short-lived one.

### Example: an Issue from mention to PR

1. Someone opens an Issue, or comments on an existing one, with `@jiffy add a health-check endpoint that returns the service version`.
2. The workflow fires on `issue_comment`, confirms the `@jiffy` mention with a `contains()` check, then uses `curl` against the Gitea REST API to fetch the issue body and every comment.
3. It joins them into one thread and posts it to `/api/gitea/ingestion` with `X-JIFFY-TOKEN` set to `JIFFY_GITEA_INGEST_TOKEN`. The Gateway queues a task.
4. Once the Agent finishes, it pushes a branch and opens a Pull Request, and the Gateway posts the summary back as a comment on the same Issue, using `GITEA_ACCESS_TOKEN` to authenticate the callback.
