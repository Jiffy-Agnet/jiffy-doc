## Overview

GitHub Actions runs the Edge Component directly — no relay or bridge needed. A workflow file in the repository triggers on new Issues and Issue comments, checks for `@jiffy`, and forwards the thread straight to the Gateway.

```
  Issue or comment      ┌──────────────────────┐                     ┌───────────────────┐
  mentioning @jiffy ──▶ │    GitHub Actions    │ ──────────────────▶ │      Gateway      │
  on your repository    │  runs the workflow   │  POST               │  authenticates    │
                        │                      │  /api/github/       │  and queues       │
                        └──────────────────────┘  ingestion          └───────────────────┘
```

The two credentials involved are easy to mix up: the **ingestion secret** authenticates the workflow to the Gateway, while the **git provider token** (a separate, longer-lived PAT) is what the Agent later uses inside the sandbox to push a branch and open the Pull Request. Never use the workflow's default `GITHUB_TOKEN` for that second purpose — it expires before the Agent gets to it, since the push happens asynchronously after the workflow run ends.

## Setting up the Action

<Steps>
<Step>
### Add the repository secrets and variables

Under **Settings → Secrets and variables → Actions**:

| Name | Kind | Value |
|---|---|---|
| `JIFFY_GATEWAY_URL` | Secret | Your Gateway's base URL, e.g. `https://jiffy.example.com` |
| `JIFFY_GITHUB_INGEST_TOKEN` | Secret | The value of `GITHUB_INGEST_TOKEN` from the Gateway's `.env` |
| `JIFFY_REPO_PAT` | Secret | A fine-grained PAT with Contents (Read/Write) and Pull requests (Read/Write) on this repo |
| `JIFFY_BOT_LOGIN` | Variable | The bot account's GitHub login, used to tell agent replies apart from human ones |
| `JIFFY_USER_WHITELIST` | Variable (optional) | Comma-separated GitHub usernames allowed to trigger Jiffy |
</Step>

<Step>
### Add the workflow

Create `.github/workflows/jiffy.yml`:

```yaml title=".github/workflows/jiffy.yml"
name: Jiffy Dispatch

permissions:
  contents: write
  pull-requests: write
  issues: write

on:
  issues:
    types: [opened]
  issue_comment:
    types: [created]

jobs:
  dispatch:
    runs-on: ubuntu-latest
    if: |
      (github.event_name == 'issues' && contains(github.event.issue.body, '@jiffy')) ||
      (github.event_name == 'issue_comment' && contains(github.event.comment.body, '@jiffy'))
    steps:
      - name: Collect thread and dispatch to Jiffy Gateway
        uses: actions/github-script@v9
        env:
          JIFFY_URL: ${{ secrets.JIFFY_GATEWAY_URL }}
          JIFFY_INGEST_TOKEN: ${{ secrets.JIFFY_GITHUB_INGEST_TOKEN }}
          JIFFY_BOT_LOGIN: ${{ vars.JIFFY_BOT_LOGIN }}
          JIFFY_USER_WHITELIST: ${{ vars.JIFFY_USER_WHITELIST }}
          REPO_TOKEN: ${{ secrets.JIFFY_REPO_PAT }}
        with:
          script: |
            const issueNumber = context.payload.issue.number;
            const whitelist = (process.env.JIFFY_USER_WHITELIST || '')
              .split(/[\s,]+/).map(s => s.trim().toLowerCase()).filter(Boolean);
            if (!whitelist.includes(String(context.actor).toLowerCase())) {
              console.log('Not in user_whitelist — skipping.');
              return;
            }

            const issue = await github.rest.issues.get({ ...context.repo, issue_number: issueNumber });
            const comments = await github.paginate(github.rest.issues.listComments, { ...context.repo, issue_number: issueNumber });
            const botLogin = process.env.JIFFY_BOT_LOGIN || '';

            const turns = [
              { role: 'user', author: issue.data.user.login, body: issue.data.body || '', created_at: issue.data.created_at },
              ...comments.map(c => ({
                role: c.user.login === botLogin ? 'agent' : 'user',
                author: c.user.login, body: c.body || '', created_at: c.created_at,
              })),
            ];

            const repoToken = process.env.REPO_TOKEN;
            const payload = {
              repo: { url: `https://github.com/${context.repo.owner}/${context.repo.repo}.git`, token: repoToken, username: context.actor },
              issue: { turns, external_issue_id: String(issueNumber) },
              callback: {
                url: `https://api.github.com/repos/${context.repo.owner}/${context.repo.repo}/issues/${issueNumber}/comments`,
                secret: repoToken,
              },
            };

            const response = await fetch(`${process.env.JIFFY_URL}/api/github/ingestion`, {
              method: 'POST',
              headers: { 'Content-Type': 'application/json', 'X-JIFFY-TOKEN': process.env.JIFFY_INGEST_TOKEN },
              body: JSON.stringify(payload),
            });
            if (response.status >= 400) {
              core.setFailed(`Jiffy ingestion failed: ${response.status} ${await response.text()}`);
            }
```

`issue_comment` matters as much as `issues` — most tasks are requested in a follow-up comment, not in the original Issue body. Omitting it is the most common reason a mention never triggers anything.

<Callout type="warn">
If `JIFFY_USER_WHITELIST` is unset or empty, the workflow posts a one-time comment on the Issue explaining that Jiffy is disabled on the repo and how to enable it, and does not forward anything to the Gateway.
</Callout>
</Step>

<Step>
### Commit it to the default branch

GitHub only runs Issue-triggered workflows from the repository's default branch — one that only exists on a feature branch never fires, no matter how many Issues get opened.
</Step>
</Steps>

## Environment variables

| Variable | Stored on | Sensitive |
|---|---|---|
| `JIFFY_GATEWAY_URL` | Repository (variable) | No |
| `JIFFY_GITHUB_INGEST_TOKEN` | Repository (secret) | Yes |
| `JIFFY_REPO_PAT` | Repository (secret) | Yes |
| `JIFFY_BOT_LOGIN` | Repository (variable) | No |
| `JIFFY_USER_WHITELIST` | Repository (variable, optional) | No |

The ingestion secret is per-provider and generated for you — it's the `GITHUB_INGEST_TOKEN` the Gateway's installer wrote into `.env`, never something you invent. It's only ever valid on `/api/github/ingestion`.

## Rotating the ingestion secret

Anyone holding `JIFFY_GITHUB_INGEST_TOKEN` can submit tasks to your Gateway through the GitHub route — never inline it in the workflow file, print it in a log, or paste it into an Issue or Pull Request.

To rotate it: set a new value for `GITHUB_INGEST_TOKEN` on the Gateway and restart it, then update the `JIFFY_GITHUB_INGEST_TOKEN` secret in every repository connected via GitHub, and trigger a test mention to confirm. This never affects GitLab or Gitea — each provider's secret is independent. Between updating the Gateway and updating a given repository, that repository gets an authentication failure, so rotate during a quiet period if you have many repositories connected.

## Example: an Issue from mention to PR

1. Someone opens an Issue, or comments on an existing one, with `@jiffy add a health-check endpoint that returns the service version`.
2. The workflow fires on the `issue_comment` event, confirms the mentioning user is in `JIFFY_USER_WHITELIST`, and collects the full thread — the Issue body plus every comment, in order, not just the one with the mention.
3. It posts that thread to `/api/github/ingestion` with `X-JIFFY-TOKEN` set to `JIFFY_GITHUB_INGEST_TOKEN`. The Gateway queues a task.
4. If you comment `@jiffy` again on the same Issue while that task is still running, the Gateway responds `202 Accepted` with `{"status": "already_queued"}` — expected, not an error.
5. Once the Agent finishes, it pushes a branch and opens a Pull Request, and the Gateway posts a summary with a link to that PR back as a comment on the same Issue.

If the workflow runs but nothing reaches the Gateway, see [Troubleshooting](/docs/ecosystem/edge-component/troubleshooting) for what each response means.
