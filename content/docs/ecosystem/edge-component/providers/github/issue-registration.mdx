An Issue is how work is requested from Jiffy on GitHub. There is no separate queue, dashboard, or command interface — the Issue thread is both the request and the record.

## How GitHub tracks Issues

Every GitHub repository has a built-in Issue tracker. An Issue has a title, a body, and an ordered list of comments, and it stays open until someone closes it. That structure is exactly what Jiffy consumes: the thread is the task specification.

| Part of the Issue | How Jiffy uses it |
|---|---|
| Title | Context for the task, and the basis of the automatically derived branch name |
| Body | The original request, read as part of the requirements |
| Comments | Later clarifications, corrections, and the mention itself |
| Thread order | Preserved, so the Agent can tell an earlier rejected approach from the current one |

## Registering a task

<Steps>
<Step>
### Open an Issue, or use an existing one

Describe what you want done in ordinary language. Both paths work equally well:

- **A new Issue** — write the request in the body and mention `@jiffy` there.
- **An existing Issue** — add a comment mentioning `@jiffy`, once the thread already contains enough context.

The second form is the common one. A discussion happens, the requirement settles, and someone then hands it to Jiffy.
</Step>

<Step>
### Mention Jiffy

Write `@jiffy` followed by the instruction, for example:

```text
@jiffy add a health-check endpoint that returns the service version
```

The mention can appear anywhere in the body or comment — beginning, middle, or end.
</Step>

<Step>
### The Edge Component evaluates the event

GitHub Actions starts the Edge Component workflow. Its first action is to check for a valid mention. If none is present it exits immediately, no request is made, and the Gateway never learns the event happened.

<Callout type="info">
📷 Screenshot placeholder — insert a screenshot here showing: an Issue comment containing an @jiffy instruction, immediately followed in the timeline by the workflow run indicator.
</Callout>
</Step>

<Step>
### The full thread is collected and forwarded

Once the mention is confirmed, the Edge Component collects the **entire** thread — the original Issue body plus every comment, in order — not just the comment that carried the mention. That complete thread is posted to `/api/github/ingestion`.
</Step>

<Step>
### The report comes back to the same thread

When the task finishes, the completion report is posted as a comment on the same Issue, with a link to the Pull Request. The thread that started the task is also where the result lands.

</Step>
</Steps>

## How the mention is validated

Mention matching is exact and deliberately narrow. A mention is treated as a task request only when all of the following hold:

| Condition | Detail |
|---|---|
| The text matches the configured mention | Matching is exact. A different spelling or a different name does not match |
| It appears in an Issue body or an Issue comment | Other event types, such as a label change or an assignment, carry no new text to match against |
| It is not inside a fenced code block | Text in a code block is documentation or an example, never an instruction |
| It is not inside a quoted reply | Quoting an earlier message that mentioned Jiffy does not re-trigger the task |

The last two rules exist so that writing about Jiffy in an Issue does not accidentally start a task. Discussing the mention in a code block is safe.

<Callout type="warn">
GitHub's own autocomplete may offer a real GitHub user or organization whose name resembles the configured mention. Selecting it inserts a link to that account rather than plain text, which changes what is written in the body. Type the mention out rather than accepting an autocomplete suggestion.
</Callout>

## One task per Issue at a time

The Gateway holds a lock for each Issue with a task in flight. A second mention on the same Issue while the first task is still running is acknowledged with `202 Accepted` and `{"status": "already_queued"}`, and no second task is created.

This is what prevents one Issue from producing two sandboxes, two branches, and two competing Pull Requests. Once the first task finishes, mentioning Jiffy again on the same Issue starts a new task normally.

If a mention produced no reaction at all, see [Troubleshooting](/docs/submodules/edge-component/introduction/troubleshooting).
