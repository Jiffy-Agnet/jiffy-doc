The Edge Component is the first stage of the Jiffy pipeline and the only stage that knows anything about your git provider. It is a lightweight component that runs alongside each provider — a GitHub Action, a Gitea Action, or a webhook relay for GitLab — inside or next to the repository you want Jiffy to work on.

It exists to answer exactly one question before any other part of Jiffy is involved: **was Jiffy actually mentioned?** If the answer is no, the Edge Component stops immediately and the Gateway never sees the event at all. If the answer is yes, it collects the full Issue thread and forwards it to the Gateway as a single pre-filtered payload.

## Where it sits in the pipeline

```
  Issue or comment          ┌────────────────────┐                      ┌───────────────────┐
  mentioning @jiffy   ────▶ │   Edge Component   │ ───────────────────▶ │      Gateway      │
  on your provider          │  GitHub Action /   │  filtered payload    │  authenticates,   │
                            │  GitLab relay /    │  X-JIFFY-TOKEN       │  queues the task  │
                            │  Gitea Action      │  header              └───────────────────┘
                            └────────────────────┘
```

Everything downstream of the Edge Component is provider-agnostic. The Gateway, the sandbox, and the Agent all work from the same normalized payload regardless of whether the task started on GitHub, GitLab, or Gitea.

## What makes it deliberately small

| Property | Detail |
|---|---|
| Lifetime | Per event — it starts, evaluates the event, and exits |
| State | None. It stores nothing and remembers nothing between runs |
| Responsibility | Detect the mention, collect the thread, forward it |
| Not its responsibility | Authentication decisions, deduplication, queuing, execution, reporting |
| Authentication | Sends a per-provider shared secret in the `X-JIFFY-TOKEN` header |

Because it holds no state and makes no decisions beyond mention detection, adding a new channel to Jiffy means writing a new Edge Component that speaks the Gateway's ingestion contract — not changing the Gateway, the sandbox, or the Agent.

<Callout type="info">
Each provider gets its own independently configured ingestion secret. A secret is never shared across providers, so a leaked GitHub secret cannot be used to submit tasks through the GitLab or Gitea ingestion route.
</Callout>
