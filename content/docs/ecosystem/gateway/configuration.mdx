The Gateway is configured entirely through environment variables, read once at startup from the process environment or from a `.env` file next to the project. There is no configuration stored in the database and nothing to configure per repository — a repository becomes a Jiffy repository by installing the Edge Component, not by registering it here.

The variables fall into seven groups.

## Ingestion secrets

Each provider route has its own secret, and they are never shared.

| Variable | Route it protects |
|---|---|
| `GITHUB_INGEST_TOKEN` | `POST /api/github/ingestion` |
| `GITLAB_INGEST_TOKEN` | `POST /api/gitlab/ingestion` |
| `GITEA_INGEST_TOKEN` | `POST /api/gitea/ingestion` |

A route whose secret is unset rejects every request, including requests that send no token at all. That is the intended behavior: a provider you have not configured is a provider that cannot submit work.

<Callout type="warn">
Generate these as long random values, one per provider, and rotate them on both sides at the same time. Rotating on the Gateway alone means every repository using that provider starts receiving `401 Unauthorized` until its stored secret is updated too.
</Callout>

## The sandbox image and its resource limits

| Variable | Default | What it controls |
|---|---|---|
| `SANDBOX_IMAGE` | `jiffy-sandbox:1.2.0` | The image tag every task's container is started from. If the tag is not present locally, the Gateway builds it from the sandbox Dockerfile in the repository and tags it |
| `SANDBOX_MEMORY_LIMIT` | `2g` | The hard memory ceiling applied to each sandbox container |
| `SANDBOX_MEMORY_SWAP_LIMIT` | `4g` | The **combined** memory + swap ceiling. Must be at least the memory limit; `-1` means unlimited swap |
| `SANDBOX_CPU_LIMIT` | `1.5` | The container's CPU quota in (fractional) cores — a share of the host's processors, not a selection of specific ones |
| `SANDBOX_NODE_MAX_OLD_SPACE_MB` | *(derived)* | The Node.js heap ceiling in MiB. Unset means half the memory limit, never below 512 |
| `SANDBOX_PACKAGE_CONCURRENCY` | `2` | How many install, download, and build jobs package managers may run in parallel inside the sandbox |

The image is checked twice — once when a worker becomes ready and once again immediately before each task's container is provisioned — so an image removed between those two moments is rebuilt rather than causing a confusing failure.

<Callout type="warn">
Two of these changed meaning recently. `SANDBOX_CPU_LIMIT` used to be a processor *set* (`0-3` selecting four specific cores); it is now a share, so `1.5` is valid and `0-3` is not. And `SANDBOX_MEM_LIMIT` was renamed to `SANDBOX_MEMORY_LIMIT` — the old name is still honored as a fallback, so existing `.env` files keep working, but new configuration should use the new one.
</Callout>

The full behavior of each — including what happens when a value is unparseable, and how the package-manager caps are injected into the container — is in [Resource Limits & Network](/docs/ecosystem/sandbox/configuration).

## Execution parallelism and the run window

| Variable | Default | What it controls |
|---|---|---|
| `CELERY_WORKER_CONCURRENCY` | `1` | How many tasks one worker process runs at the same time |
| `SANDBOX_AGENT_TIMEOUT` | `3600` | How long, in seconds, a single Agent run may take before the Gateway gives up and fails the task |

Each concurrency slot can hold one full sandbox container, so these two variables together decide how much of the host Jiffy may occupy: **worker concurrency × `SANDBOX_MEMORY_LIMIT`** is the memory to plan for. The default of one deliberately serialises execution, which is the right choice on a constrained host — a second sandbox starting while the first is mid-installation is the classic way to get both killed.

<Callout type="info">
The worker reads this from settings rather than from a command-line flag, and the bundled Compose files deliberately pass **no** `--concurrency` argument so that the environment variable is what applies. If you run the worker by hand and pass `--concurrency` yourself, your flag wins.
</Callout>

The run window is enforced by the Gateway itself: it starts the Agent detached and polls for completion, rather than holding one long request open for the whole run. When the budget is exhausted the task fails and the container is torn down.

## Cleanup behavior

| Variable | Default | What it controls |
|---|---|---|
| `JIFFY_SANDBOX_CLEANUP` | `true` | Whether the sandbox container is stopped and removed after each task |

Set this to `false` and containers are left running after their task ends, which lets you attach to one and inspect exactly what the Agent left behind. That is genuinely the fastest way to diagnose a stubborn task.

<Callout type="warn">
This is a debugging setting, not a production one. With cleanup disabled, every task leaves a container behind permanently — including the memory reserved by its limit. Turn it back on when you are done.
</Callout>

## The network allowlist

Sandbox containers are restricted by default: outbound connections are limited to a list of hostnames, enforced with firewall rules applied inside the container's own network namespace.

| Variable | Default | What it controls |
|---|---|---|
| `JIFFY_SANDBOX_NETWORK_RESTRICTED` | `true` | Set to `false` to disable the restriction entirely and give the sandbox open egress |
| `SANDBOX_NETWORK_ALLOWLIST` | The built-in list below | A comma-separated list of hostnames. Setting this **replaces** the built-in list |
| `SANDBOX_NETWORK_ALLOWLIST_EXTRA` | *(unset)* | A comma-separated list of hostnames **appended** to whichever list is in effect |

The built-in list covers the common package registries and the hosted git providers:

```
pypi.org, files.pythonhosted.org, registry.npmjs.org,
crates.io, static.crates.io, proxy.golang.org, sum.golang.org,
github.com, api.github.com, objects.githubusercontent.com,
codeload.github.com, gitlab.com, gitea.com
```

The two list variables exist because they solve different problems. Use `SANDBOX_NETWORK_ALLOWLIST_EXTRA` for the things that vary per installation and simply cannot be shipped as defaults — your self-hosted git server, and the endpoint your model provider lives behind. Use `SANDBOX_NETWORK_ALLOWLIST` only when you deliberately want to narrow the world down to your own mirrors.

<Callout type="warn">
A self-hosted git server almost always needs an entry in `SANDBOX_NETWORK_ALLOWLIST_EXTRA`. Without it the restriction is applied successfully, the container starts fine, and then the clone fails — which looks nothing like a networking problem until you know to look for it.
</Callout>

Both lists are merged, lowercased, and deduplicated before use, and the effective list is logged at the start of every run alongside whether restriction was active at all.

## The Docker connection

The worker manages sandbox containers through the Docker engine, and how it reaches that engine depends on where the worker itself runs.

| Variable | When you need it |
|---|---|
| `DOCKER_HOST` | **Required** when the worker runs inside a container. Point it at the socket proxy, for example `tcp://docker-socket-proxy:2375` |

Running the worker directly on the host, this can be left unset — the Docker library finds the default socket on its own. The Gateway checks this up front: if the variable is unset *and* the default socket is unreachable, it raises an explicit error naming the variable rather than letting the connection fail mysteriously later.

Every Docker client the Gateway creates carries a request timeout of at least **fifteen minutes**. That covers the slowest single call the Gateway makes, which is building the sandbox image — it no longer has anything to do with how long a task may run. The Agent is started detached and polled for completion, so its window is governed by `SANDBOX_AGENT_TIMEOUT` alone and no single request has to survive for the length of the run.

<Callout type="info">
This is why the change was made. A blocking call held one connection open for the whole run, and the Docker Socket Proxy in the bundled stack closes any connection after ten minutes. Every run longer than that ended in a disconnect that surfaced as a confusing failure, while the Agent itself carried on working inside a container nobody was watching any more.
</Callout>

## The deployment image

| Variable | Default | What it controls |
|---|---|---|
| `JIFFY_GATEWAY_IMAGE_VERSION` | `dev` | Which published Gateway image tag the production Compose file runs |

The production Compose file pulls `ghcr.io/jiffy-agnet/gateway` at this tag rather than building the image locally, so starting the stack no longer waits on a build. `dev` tracks the development branch; pin it to a released version tag for a deployment you want to stay put.

<Callout type="info">
This applies to the `web` and `celery` services — the Gateway itself. It is unrelated to `SANDBOX_IMAGE`, which is the image tasks run *inside* and is still built on the host when it is missing.
</Callout>

## Supporting services

| Variable | Default | What it controls |
|---|---|---|
| `REDIS_URL` | `redis://127.0.0.1:6379/0` | Where the Issue locks and the task payloads live |
| `CELERY_BROKER_URL` | `redis://127.0.0.1:6379/1` | The queue the worker consumes from |
| `CELERY_RESULT_BACKEND` | `redis://127.0.0.1:6379/2` | Where Celery stores task results |
| `SECRET_KEY` | An insecure development value | Must be set to a real random value in any deployment |
| `DEBUG` | `False` | Leave off outside local development |
| `ALLOWED_HOSTS` | `localhost,127.0.0.1` | Comma-separated hostnames the Gateway will answer for |

Three separate Redis databases are used on purpose: the locks and payloads, the queue, and the results each have very different lifetimes and clearing one should never disturb the others.

<Callout type="info">
Task records live in a SQLite file under the project's data directory. That is a deliberate choice for a component that writes a handful of rows per task — but it does mean the data directory is the one thing worth putting on durable storage.
</Callout>
