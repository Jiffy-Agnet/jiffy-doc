The sandbox has no configuration of its own. Everything about it is decided by the Gateway, using environment variables read when the Gateway starts, and applied when each container is created. There is nothing to configure per repository and nothing that persists between tasks.

## The image

| Variable | Default | What it controls |
|---|---|---|
| `SANDBOX_IMAGE` | `jiffy-sandbox:1.2.0` | The image tag every sandbox container is started from |

The Gateway checks for this tag locally before each task. If it is present, the check costs almost nothing. If it is missing, the Gateway builds it from the sandbox Dockerfile that ships with the Gateway repository and tags it with exactly that value — so a fresh host works without a separate build step, at the cost of several minutes on its first task.

You can also build it yourself ahead of time using the build script in the Gateway repository, including against a registry target if you would rather distribute the image than rebuild it on every host.

<Callout type="info">
Change `SANDBOX_IMAGE` to a tag that does not exist locally and the Gateway will build the bundled Dockerfile and give it that name — which is very likely not what you meant. To use a genuinely different image, make sure it is present on the host first.
</Callout>

## Resource limits

| Variable | Default | What it controls |
|---|---|---|
| `SANDBOX_MEMORY_LIMIT` | `2g` | The hard memory ceiling for each sandbox container |
| `SANDBOX_MEMORY_SWAP_LIMIT` | `4g` | The **combined** memory + swap ceiling. The difference between the two is how far the container may spill into swap instead of being killed |
| `SANDBOX_CPU_LIMIT` | `1.5` | The container's CPU quota, in (fractional) cores |

The defaults assume the host can spare roughly 2 GB of memory and 1.5 cores for each task running at the same time. Size the host as *worker concurrency × memory limit* — see [Resource Management & Sizing](/docs/ecosystem/resource-management).

### Memory and swap go together

The two memory variables are not independent. `SANDBOX_MEMORY_SWAP_LIMIT` is the combined memory + swap ceiling that the container runtime expects alongside the memory limit, so it must be **greater than or equal to** `SANDBOX_MEMORY_LIMIT`. With the defaults, a container gets 2 GB of memory and may spill up to a further 2 GB into the host's swap before anything is killed.

That headroom is the entire point. A heavy dependency installation that briefly exceeds its memory ceiling gets slower rather than getting killed outright.

| Value you set | What happens |
|---|---|
| A size greater than or equal to the memory limit | Used as-is |
| `-1` | Unlimited swap |
| Smaller than the memory limit, or unparseable | The Gateway logs a warning and uses **twice** the memory limit instead |

The same fallback applies to the memory limit itself: an unparseable value is logged and replaced with the `2g` default, so a typo degrades to the documented behavior rather than to no limit at all.

<Callout type="info">
`SANDBOX_MEM_LIMIT` — the older name — is still read as a fallback for `SANDBOX_MEMORY_LIMIT`, so an existing `.env` keeps working. Prefer the new name in anything you write from now on.
</Callout>

### CPU is a share, not a processor number

`SANDBOX_CPU_LIMIT` is a quota expressed in cores, the same thing `docker run --cpus` accepts. Fractions work: `1.5` gives a container one and a half cores' worth of time, `0.5` gives it half a core, `4` gives it four cores' worth.

<Callout type="warn">
This changed. `SANDBOX_CPU_LIMIT` used to be passed through as a processor *set*, where `4` meant "processor number four" and failed outright on a host without one. It is now a share, so a value carried over from an older `.env` means something different than it used to — `0-3` is no longer valid, and `4` no longer pins a core. A value that is not a positive number is logged and replaced with `1.5`.
</Callout>

## Package-manager memory pressure

Running out of memory during `npm install` — not during the actual work — is the most common way a sandbox dies, and the symptom is unhelpful: a process killed with **exit code 137** and no error explaining why. So the Gateway caps the package managers before the Agent can run anything.

| Variable | Default | What it controls |
|---|---|---|
| `SANDBOX_NODE_MAX_OLD_SPACE_MB` | *(derived)* | The Node.js heap ceiling, in MiB. Unset means half the container's memory limit, never below 512 |
| `SANDBOX_PACKAGE_CONCURRENCY` | `2` | How many install, download, and build jobs package managers may run in parallel |

These are applied in two places when the container is created:

- **Into the container's environment**, so they are in effect for every command the Agent runs: `NODE_OPTIONS=--max-old-space-size=…`, `npm_config_maxsockets`, `npm_config_jobs`, `CARGO_BUILD_JOBS`, `MAKEFLAGS=-j…`, and `GOMAXPROCS`. Progress output, funding messages, and audit checks are switched off in the same pass, since they cost time and add nothing to a non-interactive run.
- **Into pnpm's own configuration file**, because pnpm reads its network and child concurrency only from there and ignores the `npm_config_*` variables entirely. This step is best-effort: if it fails, installs simply run at the image's default parallelism and the task carries on.

The Agent is told about all of this in its instructions — that the sandbox has a hard cap, that exit code 137 means memory rather than a mistake in its change, and that it should retry with *lower* parallelism instead of raising the limits.

<Callout type="info">
Leaving `SANDBOX_NODE_MAX_OLD_SPACE_MB` unset is usually right. Derived from the memory limit, the heap ceiling tracks whatever memory you give the container, so raising `SANDBOX_MEMORY_LIMIT` raises it too without a second edit.
</Callout>

## The Agent's run window

| Variable | Default | What it controls |
|---|---|---|
| `SANDBOX_AGENT_TIMEOUT` | `3600` | How long, in seconds, a single Agent run may take before the Gateway gives up and fails the task |

The Gateway enforces this itself. It starts the Agent detached and polls for completion every few seconds, logging progress every five minutes, so the window is a real budget rather than a side effect of whatever request timeout the Docker client or an intermediate socket proxy happens to use — see [Container Lifecycle](/docs/ecosystem/sandbox/lifecycle).

When the budget runs out the task fails and the container is torn down, which kills the run with it. Values below sixty seconds are raised to sixty.

## Cleanup

| Variable | Default | What it controls |
|---|---|---|
| `JIFFY_SANDBOX_CLEANUP` | `true` | Whether the container is stopped and removed when the task ends |

Set it to `false` and the container is left running after its task finishes, which is the only way to inspect what the Agent actually left behind — the working tree, the installed dependencies, the result file it wrote.

<Callout type="warn">
This is a debugging setting. With it disabled, every task leaves a container behind permanently, each holding its memory reservation. Turn it back on and remove what accumulated once you are finished.
</Callout>

## The network allowlist

| Variable | Default | What it controls |
|---|---|---|
| `JIFFY_SANDBOX_NETWORK_RESTRICTED` | `true` | Set to `false` to disable the restriction entirely and give the sandbox open egress |
| `SANDBOX_NETWORK_ALLOWLIST` | The built-in list below | Comma-separated hostnames. Setting this **replaces** the built-in list |
| `SANDBOX_NETWORK_ALLOWLIST_EXTRA` | *(unset)* | Comma-separated hostnames **appended** to whichever list is in effect |

The built-in list:

```
pypi.org, files.pythonhosted.org, registry.npmjs.org,
crates.io, static.crates.io, proxy.golang.org, sum.golang.org,
github.com, api.github.com, objects.githubusercontent.com,
codeload.github.com, gitlab.com, gitea.com
```

The two list variables answer different needs, and picking the right one matters:

**Reach for `SANDBOX_NETWORK_ALLOWLIST_EXTRA` almost always.** It is for the hosts that vary per installation and therefore cannot be shipped as defaults — your self-hosted git server, and the endpoint your model provider sits behind. It adds to the defaults rather than replacing them, so package installation keeps working.

```bash
SANDBOX_NETWORK_ALLOWLIST_EXTRA=git.example.com,llm.example.com
```

**Reach for `SANDBOX_NETWORK_ALLOWLIST` only when you mean to narrow things down.** It replaces the built-in list entirely, which is what you want if every dependency comes from your own mirrors and you would rather the public registries were not reachable at all.

```bash
SANDBOX_NETWORK_ALLOWLIST=git.example.com,pypi.example.com
```

Both lists are merged, lowercased, and deduplicated before use. The effective result is logged at the start of every run, and repeated in the container's own startup report.

<Callout type="warn">
Turning `JIFFY_SANDBOX_NETWORK_RESTRICTED` off gives a model-driven agent unrestricted outbound network access from a container holding your repository access token. It is a useful thing to do for five minutes while isolating a problem, and a poor thing to leave in place.
</Callout>

## The Agent's model configuration

There is **no environment variable for this**. The Gateway reads the OpenCode configuration file from its own project root and writes it directly into each container at startup rather than mounting it — which is what lets the Gateway's worker run inside a container itself, since a mount would need a path the Docker engine can see on the host.

<Callout type="info">
`SANDBOX_OPENCODE_CONFIG_PATH` used to appear in `.env.example` and in the Compose files. It was never actually read, and it has been removed. Delete it from your own `.env` if it is still there — setting it has no effect.
</Callout>

The image also carries a working default configuration pointed at OpenCode's built-in free-tier models, so the container starts successfully and the Agent has a model to work with even when nothing custom has been provided.

Whatever endpoint that configuration points at needs to be reachable from inside the sandbox. If it is not one of the built-in allowlisted hosts, add it to `SANDBOX_NETWORK_ALLOWLIST_EXTRA`.
