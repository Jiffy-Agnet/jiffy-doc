Sandbox problems have a useful property: they cluster tightly around the three things the sandbox actually controls. The image it starts from, the network it is allowed to reach, and the resources it is allowed to use. Almost every symptom lands in one of those three.

Two places tell you which:

- **The Gateway's worker log**, where every line for a task is prefixed with `[task_id]`.
- **The container's startup report**, printed the moment the container comes up, listing every runtime version, every tool, the user it is running as, whether the network is restricted, and the effective allowlist.

## Quick reference

| Symptom | Most likely cause |
|---|---|
| The task fails before the container exists | The image is missing and the build failed |
| The first task on a new host takes several extra minutes | The image is being built. This is expected, once |
| The container starts, then the clone fails | The git host is not on the allowlist, or the access token is wrong |
| A dependency installation fails to reach its registry | That registry is not on the allowlist |
| An installation or build dies abruptly with no clear error | The memory limit was exceeded |
| The container fails to start at all with a processor error | `SANDBOX_CPU_LIMIT` names a processor the host does not have |

## Image and build problems

**The build takes minutes on a fresh host.** This is normal and it happens once. If `SANDBOX_IMAGE` is not present locally, the Gateway builds it from the bundled Dockerfile before provisioning. Both the found path and the built path are logged with their elapsed time, so the log distinguishes a slow first run from a slow every run without ambiguity.

**The build fails.** Two causes cover nearly all of them: the build host cannot reach the sources the image pulls its tooling from, or the disk is full. The worker log reports that the build failed and how long it ran, but the build output itself is much more informative — build the image by hand on that host to see it properly.

**The image builds but a runtime is missing.** The image verifies Python, Node.js, package managers, and Go as part of the build, so a broken runtime normally fails the build rather than shipping. The exception is the Go version manager, whose installer is allowed to fail without failing the build — a Go toolchain is installed directly regardless, so Go itself works, but the version manager may not be there to switch versions with. The startup report shows exactly what the running container has.

<Callout type="info">
When a task behaves strangely and you suspect the environment, read the startup report first. It is a complete inventory of the container as it actually exists, which is faster than inferring what the image should have contained.
</Callout>

## The allowlist blocking something legitimate

This is the most common sandbox problem, and its signature is distinctive: **provisioning reports no problem at all, and then something fails to connect.** The restriction applied successfully — it is simply doing its job to a host you needed.

The built-in list covers the common package registries and the hosted git providers. Anything outside that has to be added.

### A self-hosted git server

The clone fails immediately after the container starts. The built-in list cannot include your git server, so unless it has been added, the very first thing the sandbox tries to do is blocked.

```bash
SANDBOX_NETWORK_ALLOWLIST_EXTRA=git.example.com
```

### A registry or mirror that is not on the list

Package installation fails to reach its source. Watch out for registries that are not obviously named — a private registry, a company mirror, or a package that downloads a binary from a release host separate from the registry itself. Native dependencies are frequent offenders here, because installing them often pulls a prebuilt binary from a completely different host.

Add each host it needs, and prefer `SANDBOX_NETWORK_ALLOWLIST_EXTRA` so the defaults stay intact:

```bash
SANDBOX_NETWORK_ALLOWLIST_EXTRA=registry.example.com,binaries.example.com
```

### The model provider's endpoint

The container starts, the clone succeeds, and the Agent cannot begin work. Whatever endpoint the OpenCode configuration points at has to be reachable, and it is per-installation, so it is not in the defaults.

### Confirming it is the allowlist

Set `JIFFY_SANDBOX_NETWORK_RESTRICTED` to `false` and re-run. If it now works, the allowlist is the cause and you know precisely what to add.

<Callout type="warn">
That is a diagnostic step, not a fix. Leaving it off gives a model-driven agent unrestricted outbound access from a container holding your repository access token. Add the specific hosts and turn it back on.
</Callout>

### Two behaviors that mislead

- **Name resolution still works for blocked hosts.** Queries to the container runtime's resolver are always allowed so allowlisted hosts can be resolved at all. A blocked host therefore resolves perfectly and then refuses to connect, which reads as a network fault rather than a policy decision.
- **Hosts are resolved once, at container start.** A host that fails to resolve at that moment is unreachable for the entire task, even if it recovers seconds later. This is fail-closed by design, but a resolution blip during startup presents itself much later as an unexplained connection failure.

Both cases are settled by the effective allowlist, which is logged at the start of every run and repeated in the startup report.

## Resource limit problems

### Memory

The default ceiling is one gigabyte. Exceeding it does not produce a tidy error — the process using the memory is killed, and what you see is an installation or a build dying abruptly, sometimes with nothing more than a non-zero exit code. Large front-end dependency installations and compiling native dependencies are the usual triggers.

Raise it:

```bash
SANDBOX_MEM_LIMIT=4g
```

<Callout type="info">
An installation that fails at a different point on each run, with no consistent error, is very often the memory limit rather than a flaky dependency. Raising the ceiling once is a much cheaper test than chasing the dependency.
</Callout>

### Processors

`SANDBOX_CPU_LIMIT` is a processor *set*, not a count. `SANDBOX_CPU_LIMIT=4` means processor number four, and on a host without one the container fails to start at all. To give a sandbox four processors, name them: `0-3`.

### Slow installations

Slowness is not always a limit problem. The image already raises the package manager's fetch timeout well above its default and lowers concurrency, precisely because downloads across a restricted egress path were exceeding the default and aborting installations that were otherwise fine. If installations are still slow rather than failing, the egress path is the thing to look at before the resource limits.

## When you need to look inside

Because the container is destroyed at the end of every task, nothing can be inspected after the fact by default.

Set `JIFFY_SANDBOX_CLEANUP` to `false` before re-running, and the container is left in place afterwards. You can then attach to it and see the working tree, the installed dependencies, the result file the Agent wrote, and the firewall rules as they were actually applied.

Turn cleanup back on afterwards, and remove the containers that accumulated while it was off — each one is still holding its memory reservation.
