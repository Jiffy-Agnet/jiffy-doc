The sandbox is the isolated Docker container the Gateway starts for one task and destroys when that task ends. It is where the Agent runs, where your repository is cloned, and where every command the Agent decides to run actually executes.

It is worth being precise about what that means. Jiffy hands a model-driven agent a repository and lets it install dependencies, run build tooling, and execute the project's own test suite. That is exactly what makes Jiffy useful, and it is also why none of it can be allowed to happen on the machine running the Gateway. The sandbox is the boundary that makes the useful part safe.

## Where it sits in the pipeline

```
 ┌───────────────────┐                    ┌──────────────────────────────────┐
 │      Gateway      │  starts one        │             Sandbox              │
 │  Django + Celery  │  container         │  Debian container, non-root user │
 │                   │ ─────────────────▶ │  memory + swap limits, CPU share │
 │  clones the       │                    │  egress restricted to allowlist  │
 │  repository in    │                    │  ┌────────────────────────────┐  │
 │  hands the Agent  │                    │  │  /workspace                │  │
 │  its instructions │                    │  │  your repository, cloned   │  │
 │                   │                    │  │  the Agent works here      │  │
 │  tears it down    │                    │  └────────────────────────────┘  │
 └───────────────────┘                    └──────────────────────────────────┘
```

## One container per task

Every task gets a brand new container, and that container never serves a second task. This is a stronger guarantee than it might first appear, and it buys several things at once:

| Property | Why it matters |
|---|---|
| A clean starting state | No leftover dependencies, no half-applied configuration, no stale build cache from an unrelated repository |
| No cross-task leakage | The repository access token, the callback secret, and the checked-out source of one task are simply not present when the next one runs |
| Free cleanup | Nothing needs to be reset, uninstalled, or reverted — the container is discarded whole |
| Honest failure | A task that corrupts its own environment corrupts only its own environment |

The container is torn down whether the task succeeded or failed. What survives is exactly what the Agent pushed to your git provider and what it reported back.

<Callout type="info">
Because the container is destroyed at the end, nothing inside it can be inspected after the fact. When you expect to need that, the Gateway's cleanup behavior can be turned off deliberately — see [Resource Limits & Network](/docs/ecosystem/sandbox/configuration).
</Callout>

## One generic image, not one per language

There is a single sandbox image, and it is deliberately generic. It ships version managers rather than pinned language versions, so the Agent installs the specific runtime a repository asks for at task time. One image serves a Python repository, a Node.js repository, and a Go repository without anyone maintaining three of them.

| Tool | Purpose |
|---|---|
| `nvm` | Install and select a Node.js version at task time |
| `uv` | Install a Python version and manage the project's dependencies |
| `gvm` | Install and select a Go version |
| `npm`, `pnpm` | Node.js package installation, with `pnpm` available through corepack |
| `gh`, `glab`, `tea` | The GitHub, GitLab, and Gitea command-line tools, used to push and open Pull Requests |
| `git`, `curl` | The basics |
| `build-essential` | A compiler and make, so native dependencies build rather than failing at installation |
| `iptables` | The firewall tooling the egress restriction uses |
| `opencode` | The Agent itself |

Working defaults for Node.js, Python, and Go are installed at build time and verified as part of the build, so a repository that does not pin a version still gets a functioning runtime immediately.

<Callout type="info">
Because versions are resolved from your repository rather than from the image, pinning them there — `.nvmrc`, `go.mod`, `pyproject.toml` — is the most reliable way to control which runtime the Agent ends up using.
</Callout>

One practical adjustment worth knowing about: the package manager configuration in the image raises the fetch timeout well above its default and lowers concurrency. Downloading large packages across a restricted, sometimes slow egress path was exceeding the default timeout and aborting installations that were otherwise fine.

The Gateway then lowers concurrency again at container-creation time, from `SANDBOX_PACKAGE_CONCURRENCY`, and caps the Node.js heap to fit inside the container's memory limit. The image's defaults are about slow downloads; these are about memory — an install that outgrows the container's ceiling is killed with an exit code and no explanation, which is much harder to recognize than a timeout. See [Resource Limits & Network](/docs/ecosystem/sandbox/configuration).

## What the sandbox is not

- **It is not a persistent environment.** There is nothing to keep warm between tasks and nothing to migrate when the image changes.
- **It is not a virtual machine.** Isolation comes from the container boundary, its resource limits, and its egress restriction — not from a hypervisor.
- **It is not something you interact with directly.** The Gateway starts it, the Agent works inside it, and it disappears. Configuring it means configuring the Gateway.
