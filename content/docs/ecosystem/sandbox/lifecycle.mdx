The sandbox has two jobs, and they pull in opposite directions. It has to be permissive enough that the Agent can genuinely build and test a real project, and restrictive enough that letting a model-driven agent run arbitrary commands is a reasonable thing to do. Everything about how the sandbox is built comes from balancing those two — see [Isolation Mechanisms](/docs/ecosystem/sandbox/isolation) for how the restrictive half is actually enforced.

## The life of one sandbox

<Steps>
<Step>
### It starts

The Gateway starts a container from the configured image with the repository access token in its environment, a memory ceiling, a combined memory + swap ceiling, and a CPU share. When restriction is active — the default — the container is also attached to a dedicated bridge network and granted the capability it needs to install its own firewall rules.

The same step puts the package-manager caps into the container's environment — the Node.js heap ceiling, and the parallelism limits for npm, Cargo, `make`, and Go. They are set at creation time on purpose, so they are already in effect for the very first command the Agent runs rather than being applied after an installation has begun.

On start the container prints a report of what it has: the versions of every runtime and tool, which user it is running as, whether the network is restricted, and the effective allowlist. That report is the single most useful thing to read when a task behaves unexpectedly.
</Step>

<Step>
### Its egress is locked down

Before anything else runs, the Gateway installs firewall rules inside the container. Loopback traffic is allowed, replies on already-established connections are allowed, name resolution through the container runtime's own resolver is allowed, and each allowlisted hostname is resolved so connections to its addresses can be permitted. Everything else is dropped.

If those rules cannot be installed, the container is destroyed and the task fails. The sandbox is never allowed to run unrestricted just because the restriction step did not work.
</Step>

<Step>
### The Agent's configuration is written in

The OpenCode configuration is written directly into the container rather than mounted from the host. That sounds like a detail, but it is what allows the Gateway's worker to itself run inside a container: a mount would need a path the Docker engine can see on the host, and the configuration only exists inside the worker.

pnpm's install concurrency is written in at the same point, into pnpm's own configuration file. It needs its own step because pnpm ignores the `npm_config_*` environment variables the previous step set. This one is best-effort: if it does not take, installs run at the image's default parallelism and the task continues regardless.
</Step>

<Step>
### The repository is cloned into the workspace

Your repository is cloned into `/workspace` using the access token that arrived with the task, and the working tree is explicitly moved onto `develop`. The Agent always begins from a known branch rather than whatever the remote happens to point at.
</Step>

<Step>
### The Agent runs

The Agent is started as a login shell inside `/workspace`, which is how it picks up the version managers on its path. Its output is redirected to the container's main output stream, so the container's own logs show the run live rather than only after it finishes.

It is started **detached**, and the Gateway then polls the container runtime every few seconds to ask whether it has finished, logging a progress line every five minutes. The Agent's window is `SANDBOX_AGENT_TIMEOUT` — one hour by default — and the Gateway enforces it itself. When the budget runs out, the task fails and the teardown in the next step kills the run.

<Callout type="info">
This used to be a single blocking call, and the run window was whatever request timeout the Docker client happened to carry. That broke in a specific and confusing way: the Docker Socket Proxy in the bundled stack closes any connection after ten minutes, so every longer run ended with the Gateway seeing a clean disconnect, reporting a failure with no exit code, and tearing down a container in which the Agent was still working perfectly well. Polling keeps every request short, so nothing in the path between the Gateway and the container runtime can truncate a long run.
</Callout>
</Step>

<Step>
### It is destroyed

The container is stopped and removed regardless of the outcome, unless cleanup has been deliberately disabled. Nothing inside it survives.
</Step>
</Steps>
