Everything below is needed before you run the installer, except where noted as optional. None of it is Jiffy-specific infrastructure — it's the host, the container runtime, and the credentials the Gateway and sandbox need to reach your git provider.

## Docker

Jiffy's Gateway, its Celery worker, Redis, and the sandbox all run as containers.

- **Docker Engine** 24+ and the **Compose plugin** (`docker compose`, not the standalone `docker-compose` v1)
- The user running the installer needs permission to talk to the Docker daemon (in the `docker` group, or root)

## Docker Socket Proxy

The Celery worker needs to create and manage sandbox containers, but it should never have raw access to the host's Docker socket — a compromised task container could otherwise reach everything else on the host. Jiffy puts [`tecnativa/docker-socket-proxy`](https://github.com/Tecnativa/docker-socket-proxy) in between: it's pulled automatically as part of the stack, so there's nothing to install by hand, but it does mean the host needs outbound access to pull that image (and the Gateway/sandbox images) on first run.

<Callout type="warn">
Never expose the Docker Socket Proxy on a host port. It should only be reachable from the `web`/`celery` services on the stack's internal Docker network — this is the default, and shouldn't be changed.
</Callout>

## A git provider token

Jiffy needs a token with permission to push branches and open Pull/Merge Requests on the repositories you connect. Generate one for whichever provider(s) you plan to use — you'll wire it into the matching Edge Component, not the Gateway itself:

| Provider | Token type | Required scopes |
|---|---|---|
| GitHub | Fine-grained Personal Access Token | Contents (Read/Write), Pull requests (Read/Write) |
| GitLab | Project or personal access token | `read_api`, `write_repository` |
| Gitea | Access token | `repo`, `issue` |

<Callout type="info">
Use a long-lived token, not a short-lived CI-provided one (like GitHub Actions' default `GITHUB_TOKEN`). Jiffy's push and PR happen asynchronously, after the triggering CI run has already ended.
</Callout>

## Model access (optional)

The sandbox's coding agent (OpenCode) doesn't need a separate model credential to get started — it ships with free-tier model access built in, so there's nothing to sign up for before your first task.

<Callout type="info">
Want to use a specific provider instead of the built-in free models — Anthropic's Claude, for example? Add that provider's API key as an environment variable in your Gateway configuration (for Anthropic, that's typically `ANTHROPIC_API_KEY`). Once it's set, OpenCode will offer that provider's models in the sandbox alongside the free ones. See [OpenCode's provider docs](https://opencode.ai/docs/providers/) for the exact variable name each provider expects.
</Callout>

## Minimum resource requirements

| Resource | Minimum | Notes |
|---|---|---|
| CPU | 2 vCPU | 1 for the Gateway stack (web, worker, Redis), 1 free for a running sandbox |
| Memory | 4 GB RAM | The sandbox image itself, plus whatever the task's toolchain (Node, Python, Go) needs at runtime |
| Disk | 20 GB free | Docker images (Gateway, sandbox, Redis, proxy) plus room for cloned repositories per task |
| Network | Outbound HTTPS | To your git provider, your model provider (if you've configured one), and package registries the agent may need mid-task |

<Callout type="info">
These are the floor, not a target — add more CPU and memory if you expect several sandboxes running at once. See Recommended resources below for a baseline that holds up better under everyday use.
</Callout>

## Recommended resources

For running more than the bare minimum comfortably — several sandboxes at once, or repositories with heavier toolchains — this is a more realistic baseline:

| Resource | Recommended | Notes |
|---|---|---|
| CPU | 4 vCPU | Headroom for the Gateway stack alongside two or more sandboxes running at the same time |
| Memory | 8 GB RAM | Comfortable room for larger toolchains (e.g. Node, Python, and Go all installed at once) inside a running sandbox |
| Disk | 50 GB free | More room for cloned repositories, dependency caches, and container image layers to accumulate over time |

<Callout type="info">
These aren't hard requirements, just a more comfortable baseline than the bare minimum. Scale further if your team runs many concurrent tasks or works with unusually large repositories.
</Callout>

Once these are in place, continue to [Installation](/docs/ecosystem/quickstart) for the quick-start path, or [Manual Installation](/docs/ecosystem/manual-installation) if you'd rather configure each piece by hand.
